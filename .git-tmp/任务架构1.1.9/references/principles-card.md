# 任务架构 速记卡

## 定位
面向中大型商业项目、长期维护项目、全栈工程项目、多模块系统和 AI 难以稳定维护的复杂代码库。覆盖前端、后端、API、数据库、后台任务、CLI、桌面端、移动端、EXE/安装包/Docker/SDK/插件等可交付形态、部署、测试和文档。一次性脚本、小 demo、临时实验、小型原型不调用本技能，直接使用编程智能体自身能力即可。

## JSON中文化
- 字段名、说明、状态、测试描述、变更记录必须中文
- 函数名、类名、变量名、文件路径、路由、数据库字段、第三方库名保留原样
- 禁止使用 `project/modules/contracts/changeLog` 这类英文主键名

## 三条铁律
1. JSON先行 — 先改JSON再改代码
2. JSON是法官 — 不一致时JSON对，修正代码
3. 禁止代码漂移 — 代码不得有JSON未定义的东西

## 注意力保护
- 用户本次需求优先：先锁定明确要求、不要做的事、验收信号
- 默认不全量读取：不读全部 references、全部切片、全部第4层
- 默认不全量展开：只展开本次相关功能簇、功能树、模块树
- 用户提到的页面、按钮、字段、接口、文案、状态、异常必须逐项落位
- 流程不能盖过结果；发现流程过重时，收缩到本次最小影响范围

## 受控主动性
- 用户描述的是想要什么，AI 要思考真实软件应该是什么
- 核心功能、天然绑定能力、商业级基础设施默认纳入
- 强相关衍生能力默认列出让用户砍
- 高成本/高风险扩展先询问；用户明确不要的内容必须排除并记录
- 主动推导出的能力必须分类、说明理由并落到 JSON；不能落位的只作为建议

## 受管项目自动接管
- 当前项目存在 `architecture.json` 时，默认已经进入任务架构管理
- 改代码、改 UI、修 Bug、改接口、改字段、改测试、改文件结构，都必须先改 JSON
- 用户没有输入 `/修改架构` 不是绕过 JSON 的理由
- 用户只说“使用任务架构/按技能/按架构来”但没写命令时，必须自动选择五个命令之一
- 用户明确要求跳过 JSON 时，必须说明代码漂移风险并记录“本次未更新 architecture.json”

## 六大机制
| 机制 | 做什么 | 记住 |
|------|--------|------|
| 最大主动性 | 补全应有功能和工程关注点 | 用户没说的核心链路、安全、日志、部署也要考虑 |
| 功能簇/功能树展开 | 模糊需求→应有功能→功能树→架构落位 | 一个功能名=天然绑定的一组功能，不是薄 demo |
| 专业能力索引 | 把已有技能接入功能树节点 | 只做路由和回写约束，不做总控 |
| 交互完整性 | 补全交互细节 | 每个操作：请求→反馈→异常→恢复 |
| 多层递进 | 保证思考深度 | 全景→骨架→逐块→集成，不跳步 |
| 分治设计 | 防止遗漏 | 大功能拆小块，每块一次聚焦 |

## 功能簇三段式
1. 需求语义展开 — 模糊需求 → 应有功能域
2. 功能本体展开 — 功能名 → 天然绑定的子功能、状态、交互、异常
3. 架构落位展开 — 功能簇 → 模块、入口、接口、数据、页面、测试、变更记录

## 功能树粒度
- 路径：模糊需求 → 功能簇 → 功能树 → 架构落位
- 层级：L0 产品/系统 → L1 功能域 → L2 功能组 → L3 功能 → L4 子功能/操作 → L5 状态/异常/验证责任
- 叶子节点必须可验收、可落位、可测试
- 已确认叶子节点必须有验收标准、异常路径、架构落位和验证责任
- 继续展开到不再需要猜业务含义；不要展开到代码语句级步骤

## 三层粒度
- 功能粒度：用户需求拆到可验收、可落位、可测试
- 模块粒度：工程责任拆到父模块、子模块、职责边界和依赖关系清楚
- 文件粒度：实现清单拆到文件职责单一，继续拆会进入函数级细节
- 顺序固定：先功能树，再模块树，再实现清单

## 功能簇分层
| 分类 | 行动 |
|------|------|
| 核心功能 | 默认纳入 |
| 天然绑定功能 | 默认纳入 |
| 商业标配功能 | 默认纳入 |
| 待确认扩展 | 列出并询问，不直接实现 |

## 专业能力索引
- 用于 UI、测试、安全、性能、客户端、可执行交付、部署、文档等专业能力
- 当前智能体已有对应技能时，读取最小必要部分
- 没有对应技能时，按本技能规则自行补全
- 任何专业能力产出必须回写到 architecture.json
- 不得把外部技能写成强制依赖，不得接管任务主流程

## UI质量门禁
- 涉及页面/组件/仪表盘/管理后台/编辑器时，默认要求有设计感
- 优先遵循或建立设计系统，记录布局、tokens、组件状态和响应式规则
- 优先使用已有图标库；有 Lucide/shadcn 时优先 Lucide
- 图标必须语义清晰、尺寸一致，图标按钮要有 tooltip 或可访问标签
- 可运行项目的重要 UI 修改要尽量截图或浏览器验收

## 五个命令
| 命令 | 何时用 |
|------|--------|
| `/创建架构` | 新项目从零开始 |
| `/分析架构` | 已有代码，想纳入管理 |
| `/追加架构` | 加新功能（JSON中不存在的模块） |
| `/修改架构` | 改已有模块的任何东西 |
| `/校验架构` | 检查 JSON 与代码是否漂移 |

## JSON四层
| 层 | 何时读 | 有什么 |
|----|--------|--------|
| 1.骨架 | 任何操作第一步 | 项目身份+运行形态+入口+交付物+系统集成+模块拓扑+模块树+模块详情+依赖图 |
| 2.契约 | 需要调用已有模块时 | 每个模块导出什么+依赖谁 |
| 3.清单 | 写具体模块代码时 | 文件列表+表DD+组件树 |
| 4.细节 | 写具体函数/组件时 | 参数详情+约束+测试用例 |

## 执行模板
- 第一段必须声明：自动判定命令、是否发现 architecture.json、是否受管、本次读哪些层、影响范围、最小闭环
- 修改 JSON 后必须说明：新增、修改、废弃、受影响模块、必须同步的代码/测试
- 完成前必须对照完成定义：JSON先行、代码一致、验证证据、恢复点、变更记录、剩余风险
- 失败或卡住时写失败恢复：失败阶段、失败位置、已完成、未完成、下一步、不要重复

## 模块树
- 模块拓扑回答“谁依赖谁”，模块树回答“谁包含谁”
- 父子模块只表达层级归属，不表达运行时依赖
- 子模块要记录编号、名称、父模块、子模块、职责和落位
- 跨兄弟模块、跨父模块调用必须写进 `模块拓扑.依赖图`
- 模块树叶子节点要能落到模块详情、实现清单和测试责任

## 模块详情
- 模块拓扑回答“有哪些模块、谁依赖谁”
- 模块详情回答“模块负责什么、不负责什么、内部怎么组织、边界在哪里”
- 每个模块至少记录：职责、非职责、所属功能树节点、上下游、内部结构、数据读写、错误边界、配置、安全、测试责任
- 无状态/无配置/无性能要求也要写“不适用”，不能留空

## 漂移修复
- 发现代码和 JSON 不一致时，先分类，不要直接改代码
- JSON 漏登记：代码合理则先补 JSON，再校验
- 代码越界：回收代码，或登记为待确认后评估
- JSON 设计过期：先改 JSON，再按新架构改代码
- 修复后补功能树、模块树、模块详情、接口契约、实现清单、测试责任和验证证据

## JSON切片
- 默认单 `architecture.json`；过大、长期迭代或多会话协作时再启用 `architecture/` 架构文件夹
- 切片结构：根 `architecture.json` 兼容入口 + `architecture/index.json` 总索引 + 功能、模块、页面、数据、任务切片
- `architecture/index.json` 保留项目身份、功能树摘要、模块树摘要、模块拓扑、切片清单、恢复点和变更摘要
- 修改切片必须同步总索引；跨切片依赖必须写在总索引依赖图

## 压缩恢复
- 每轮收尾更新 `上下文恢复点`
- 必须记录：当前任务、继续位置、下一步、用户明确约束、用户明确不要、未验证项、剩余风险
- 压缩或中断后先读恢复点，再读相关 JSON 层，不要从头重做

## 修改后必做
1. 跑21项自动校验
2. 结果写入变更记录
3. 联想相关节点，逐一判断是否需要同步修改
4. 汇报任务判断、影响范围、JSON变更、验证结果和剩余风险
