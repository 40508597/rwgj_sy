# 功能簇展开

**用户描述的是想要什么，AI 的职责是思考它在真实软件中应该是什么。用户说的是一个功能名称时，AI 应理解这个名称背后是一组天然绑定的子功能。"做一个卡密系统"不等于"做一个卡密生成页面"，"做一个菜单栏"不等于"画一条横条"。**

### 三段式目标

功能簇展开不是只列更多功能，而是把用户的自然语言需求翻译成完整、可实施、可追踪的软件架构：

```
第1段：需求语义展开
  模糊需求 → 应有功能域
  例："股票选股系统" → 股票数据、策略编辑、选股运行、结果展示、自选股、账号权限、数据维护

第2段：功能本体展开
  功能名 → 天然绑定的子功能、状态、交互、异常、恢复
  例："菜单栏" → 菜单项、下拉、点击行为、当前项、禁用态、快捷键、路由/命令绑定

第3段：架构落位展开
  功能簇 → 模块、运行形态、入口、接口、数据、页面/界面、交付物、系统集成、测试、变更记录
  例："评论" → comments 模块、POST/GET 接口、comments 表、评论组件、权限校验、异常测试
```

任何功能簇如果只停留在文字清单，没有形成可验收的功能树节点，也没有落到 `architecture/index.json` 或相关切片的模块/入口/接口/数据/测试中，视为未完成。

### 主动性边界

功能簇展开必须主动，但不能盲目扩张：

| 分类 | 默认动作 | 说明 |
|------|----------|------|
| 核心功能 | 默认纳入 | 没有它功能不成立，如验证接口之于卡密系统 |
| 天然绑定功能 | 默认纳入 | 功能名在真实软件中自带的状态、操作、异常、恢复 |
| 商业标配功能 | 默认纳入 | 安全、错误处理、日志、配置、测试、迁移、健康检查等 |
| 强相关衍生功能 | 默认列出让用户砍 | 批量、导入导出、统计、审计、通知、后台管理等 |
| 高成本/高风险扩展 | 先询问 | 付费、风控、法律、金融、外部服务、不可逆数据操作 |
| 用户明确不要 | 排除并记录 | 写入 `上下文恢复点.用户明确不要`，防止后续重新带回 |

默认不是浅展开。对中大型商业项目，必须先给出“应有功能全景”，再按用户本次目标和明确不要收敛范围。

### 核心原则

```
用户说的 ≠ 用户需要的全部
一个功能名 = 一个功能簇（核心功能 + 衍生功能 + 关联功能）

"菜单栏" →
  不只是菜单条本身，天然包含：
    每个菜单项的点击行为、下拉子菜单、快捷键绑定、
    菜单项的启用/禁用状态、右键上下文菜单、系统托盘菜单
  → 这些不是"额外功能"，是"菜单栏"这个词自带的东西

"卡密系统" →
  不只是卡密生成，天然包含：
    生成(单条/批量/模板)、管理列表、验证接口、
    使用记录、状态管理(未用/已用/过期/禁用)、导出
  → 这些不是用户忘了说，是"卡密系统"这个词的完整含义
```

### 展开三维度

设计前，按三个维度自动展开功能簇：

```
第1维：功能使用流程
  "这个东西的完整使用链路是什么？"
  卡密：创建→分发→使用→验证→记录→管理→统计  → 每步对应子功能

第2维：功能生命周期
  "这个东西从生到死经历什么状态？"
  卡密：未使用→已使用→已过期→已禁用  → 每个状态需要对应操作和页面

第3维：生产上下文
  "这个功能在真实产品中跟什么关联？"
  卡密→谁创建的？（账号）→怎么来的？（支付）→异常怎么办？（风控）
  → 关联功能可能需要一并考虑
```

### 通用展开器

三维度是最低要求。对中大型商业项目，必须继续按以下通用问题检查，任何功能都适用：

1. **核心对象**：这个功能管理的对象是什么？对象有哪些字段、状态、归属关系？
2. **使用链路**：用户从哪里进入，如何创建/查看/修改/完成/退出？
3. **状态生命周期**：对象从创建到归档/删除经历哪些状态？每个状态允许哪些操作？
4. **角色权限**：谁能看、谁能改、谁能审批、谁不能操作？无权限时如何反馈？
5. **数据闭环**：是否需要列表、详情、搜索、筛选、分页、导入、导出、统计、批量操作？
6. **异常恢复**：重复、过期、不存在、无权限、网络失败、外部服务失败、并发冲突如何处理？
7. **产品伴随能力**：是否天然关联配置、日志、审计、通知、后台管理、监控、测试？
8. **架构落位**：它落在哪些模块、运行形态、入口、接口、数据表、页面/界面、交付物、系统集成、文件、测试和变更记录中？

### 分层裁决

功能簇展开后，按四层分类，避免既漏功能又盲目扩展：

| 分类 | 含义 | 行动 |
|------|------|------|
| 核心功能 | 功能成立所必需 | 默认纳入 |
| 天然绑定功能 | 该功能名在真实软件中默认自带 | 默认纳入 |
| 商业标配功能 | 安全、错误、日志、权限、配置、测试、审计等工程能力 | 默认纳入 |
| 待确认扩展 | 业务策略、付费、法律、金融、安全策略、外部服务、高成本能力 | 列出并询问，不直接实现 |

### 功能树建模

功能树是功能簇和工程拓扑之间的桥。功能簇负责把用户的模糊需求展开成应有能力，功能树负责把这些能力递归拆到足够细的功能节点，再把叶子节点落到模块、入口、接口、数据、文件和测试。

功能树不是愿望清单，也不是产品脑图。它必须服务于实现：确认纳入的叶子节点必须能验收、能定位、能测试；暂不实现或需要业务判断的节点必须标为待确认或延期。

```
模糊需求 → 功能簇 → 功能树 → 架构落位 → 模块/运行形态/入口/接口/数据/页面或界面/交付物/系统集成/文件/测试
```

#### 推荐层级

| 层级 | 名称 | 说明 |
|------|------|------|
| L0 | 产品/系统 | 项目整体目标，如股票选股系统 |
| L1 | 功能域 | 业务大域，如股票数据、策略管理、选股运行 |
| L2 | 功能组 | 一组强相关能力，如策略编辑、策略版本、策略测试 |
| L3 | 功能 | 用户能感知的完整功能，如新建策略、运行策略 |
| L4 | 子功能/操作 | 可实现的操作，如保存草稿、发布版本、取消运行 |
| L5 | 状态/异常/验证责任 | 交互状态、异常路径、边界条件、测试责任 |

默认展开到 L4；涉及权限、支付、金融、风控、数据安全、异步任务、外部服务或关键商业流程时，继续展开到 L5。

#### 节点字段

功能树节点建议写入 `architecture/features/*.json` 中的 `功能树`，并由 `architecture/index.json` 汇总引用。字段名使用中文，真实代码标识符和路径保持原样。

```json
{
  "编号": "f1.2.3",
  "名称": "运行选股策略",
  "层级": "L3",
  "类型": "功能",
  "分类": "核心功能",
  "状态": "已确认",
  "父节点": "f1.2",
  "说明": "用户选择策略和股票池后触发一次选股运行",
  "子节点": ["f1.2.3.1", "f1.2.3.2"],
  "验收标准": ["能选择策略", "能选择股票池", "运行完成后生成结果"],
  "异常路径": ["策略不存在", "股票池为空", "行情数据缺失", "运行超时"],
  "架构落位": {
    "模块": ["m_strategy", "m_screening"],
    "入口": ["POST /api/screening/runs"],
    "接口": ["create_screening_run"],
    "数据": ["screening_runs", "screening_results"],
    "文件": ["src/screening/service.py"],
    "测试": ["tests/test_screening_runs.py"]
  },
  "验证责任": ["接口测试", "异常路径测试", "结果一致性测试"],
  "展开理由": "该功能包含异步运行、状态流转和结果生成，必须拆到可测试操作",
  "停止展开理由": "叶子节点已经具备触发、输入、输出、异常和测试责任"
}
```

#### 递归展开规则

继续展开的信号：
- 节点里包含多个动作，如创建、编辑、发布、撤销、删除混在一起
- 节点里包含多个角色或权限边界
- 节点里包含状态流转，如草稿、运行中、成功、失败、取消
- 节点里有异步任务、外部服务、批量操作、导入导出、支付、风控、审计
- 节点无法写出明确验收标准、异常路径或测试责任
- 节点无法落到具体模块、入口、接口、数据或文件

停止展开的条件：
- 有明确触发方式、输入、输出或结果
- 有成功标准和至少一个异常/边界判断
- 能落位到 `architecture/index.json` 或相关切片的模块、入口、接口、数据、文件、测试
- 一个不熟悉项目的开发者能据此实现，不需要继续猜业务含义
- 继续拆分只会变成代码语句级步骤，而不会增加架构可控性

停止规则反例：

```text
"导出支持 CSV"
  → 不满足停止条件：没有说明字段映射、编码、分隔符冲突、转义、异常和验证
  → 必须继续展开
  → "CSV 分隔符冲突处理"
  → 满足停止条件：输入含分隔符/引号的字段，输出正确转义后的 CSV 单元格，异常和测试可定义

"权限校验"
  → 不满足停止条件：没有说明校验对象、批量策略、权限不足策略和审计责任
  → 必须继续展开
  → "单条校验 / 批量校验 / 权限不足跳过或整体失败策略"
  → 各自满足停止条件后才可停止
```

#### 功能树与功能簇的关系

- 功能簇解决"用户没说但真实软件应有的能力是什么"。
- 功能树解决"这些能力应该细到什么程度才可实现、可追踪、可验收"。
- 功能树允许功能再次展开功能族：一个 L3 功能如果仍然过大，可以递归生成自己的 L4/L5 子功能簇。
- 功能树不能绕过用户边界。核心、天然绑定、商业标配默认纳入；高成本或强业务策略节点进入待确认扩展。

### 实现期循环展开

功能簇展开不是只发生在初始设计阶段。初始架构可以先形成可信骨架，进入逐块实现后，仍允许围绕当前功能节点和当前模块进行局部循环展开。

循环必须受控：

```text
进入实现
  ↓
发现功能缺口或细节缺口
  ↓
暂停编码
  ↓
展开当前节点相关功能族
  ↓
分类裁决：必须补 / 建议补 / 待确认 / 明确排除
  ↓
更新 `architecture/` 架构文件夹中的功能树、模块详情、接口契约、实现清单或测试责任
  ↓
继续编码和验证
  ↓
如再发现缺口，重复循环；否则退出
```

#### 触发信号

- 实现时发现缺少状态、异常路径、权限边界、数据字段、接口契约、交互反馈或验证责任。
- 测试用例无法写清楚，因为功能树节点没有明确输入、输出、成功标准或失败条件。
- 模块需要调用其他模块，但接口契约没有登记。
- 当前文件需要新增职责，但实现清单或模块详情没有承载位置。
- 代码能写出来，但无法说明它属于哪个功能树节点或如何验收。

#### 分类裁决

| 分类 | 处理 |
|------|------|
| 必须补 | 功能成立所必需，先更新架构切片，再进入本轮实现 |
| 建议补 | 真实软件常见但不影响本轮闭环，记录到功能树或未决问题，可延期 |
| 待确认 | 可能扩大范围、引入成本或改变业务策略，先问用户 |
| 明确排除 | 用户不要或本轮不做，写入恢复点或非目标，防止后续带回 |

#### 退出条件

当前循环只在满足以下条件后退出：

- 当前叶子功能有触发方式、输入、输出或结果。
- 成功标准、异常路径和验证责任已经写清。
- 涉及的模块详情、接口契约、实现清单和测试责任已经更新。
- 本轮必须补内容已实现或明确阻塞。
- 继续展开只会变成代码语句级步骤，而不会增加架构可控性。

### 反薄 Demo 规则

如果一个功能只有新增页面或新增接口，没有列表、详情、状态、异常、权限、反馈、测试、管理或记录，默认判定为薄 Demo，需要继续展开。

```
菜单栏 ≠ 一条横向导航
卡密系统 ≠ 卡密生成
任务系统 ≠ 新增任务
权限系统 ≠ 一个登录判断
选股系统 ≠ 跑一个筛选脚本
后台管理 ≠ 一个用户列表
```

### 展开流程

```
用户描述需求 → AI 第一个动作（不写代码，不画界面）：

1. 功能簇展开：
   输入："[用户说的功能名]"
   输出：
     核心功能簇（第1维，功能自身的完整使用链路）
     衍生功能簇（第2维，生命周期管理）
     关联功能簇（第3维，生产中的上下文关联）

2. 功能树建模：
   输入：已展开的功能簇
   输出：
     L0-L5 功能树节点
     每个叶子节点的验收标准、异常路径、架构落位、验证责任
     继续展开/停止展开理由

3. 向用户汇报功能全景：
   "这个功能按标准应包含：核心①-⑥，衍生⑦-⑨，关联⑩-⑪。
    建议优先做核心簇，衍生和关联根据你的实际场景决定。"

4. 用户确认范围 → 进入拆块+逐块设计
```

### 架构落位要求

功能簇确认后，必须写入 `architecture/` 架构文件夹：

- **功能树**：功能域、功能组、功能、子功能、状态/异常/验证责任；叶子节点必须有架构落位或明确待确认
- **模块拓扑**：新增/修改哪些模块，依赖谁
- **入口结构**：用户入口、接口入口、命令入口、事件入口、系统入口、资源入口
- **交付与系统集成**：交付物、系统集成、安装/发布/更新/权限/文件关联/协议唤起等
- **接口契约**：导出接口、依赖接口、参数、返回、可能异常
- **数据拓扑**：表、字段、索引、迁移、状态字段、归属关系
- **实现清单**：文件、职责、组件树、脚本、资源
- **完整细节**：测试用例、交互事件、异常路径、边界条件
- **验证证据**：自动化测试、架构校验、浏览器验收、截图、手动检查、未验证项
- **变更记录**：原因、影响范围、验证结果、剩余风险

### 展开深度

**默认标准展开（核心+衍生全部列出，让用户砍），不能默认浅展开（浅展开=用户说一个只做一个=现在的行为）。**

| 深度 | 何时用 | 内容 |
|------|--------|------|
| 标准展开 | **默认** | 核心+衍生全部列出，用户砍 |
| 浅展开 | 用户明确说"只做XX，其他不要" | 只展开核心簇 |
| 深展开 | 大型项目/用户要求完整方案 | 核心+衍生+关联全部列出，标注依赖 |
