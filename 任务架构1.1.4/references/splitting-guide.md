# 模块拆分详细指南

## 核心问题：拆还是不拆？

拆分是架构设计中最关键的决策。拆得太粗，JSON 沦为形式；拆得太细，管理成本超过收益。

## 拆分决策流程

当你面对一个功能点时，按以下顺序判断：

### 第1步：职责检验

问自己："这个模块只做一件事吗？"

- "用户认证" → 只做一件事 ✓
- "用户认证和日志记录" → 两件事，应该拆 ✗
- "数据库连接管理" → 只做一件事 ✓

### 第2步：接口检验

问自己："这个模块有明确的对外的接口（导出）吗？"

- 有可以被其他模块调用的函数/类 → 有独立接口 ✓
- 所有函数只在模块内部使用 → 无独立接口，可能是工具模块

### 第3步：依赖检验

问自己："其他模块会依赖这个模块吗？"

- 会 → 应该独立成模块
- 不会 → 考虑合并到调用它的模块

### 第4步：可测试性检验

问自己："这个模块能独立运行测试吗？"

- 能（不需要启动整个应用）→ 适合独立
- 不能（必须依赖其他模块才能测试）→ 考虑合并

### 第5步：粒度检验

问自己："这个模块拆分后有足够的代码量吗？"

- 预计少于 50 行 → 可能不值得拆
- 预计超过 500 行 → 可能需要再拆

## 常见模式

### 模式1：三层架构（推荐用于 Web 后端）

```
数据层 (m1): 数据库连接、ORM 基类
  ↓
模型层 (m2): 数据模型定义（ORM + Schema）
  ↓
服务层 (m3): 业务逻辑
  ↓
接口层 (m4): API 路由
```

每层一个模块，依赖单向流动。这是最安全的拆分方式。

### 模式2：领域驱动（推荐用于复杂业务）

```
共享基础设施 (m1): 数据库、日志、配置
  ↓
用户领域 (m2): 用户模型 + 用户服务
订单领域 (m3): 订单模型 + 订单服务
  ↓
用户 API (m4): 用户路由
订单 API (m5): 订单路由
```

每个业务领域一个模块，公共部分抽到基础设施。

### 模式3：功能模块（推荐用于 CLI 工具）

```
配置管理 (m1): 读取/解析配置
  ↓
命令A (m2): 功能A实现
命令B (m3): 功能B实现
  ↓
主入口 (m4): CLI 参数解析和分发
```

## 反面模式（应该避免）

### 反面1：过度拆分

```
❌ 不好：
m1: 仅一个数据库连接函数
m2: 仅一个 User 模型类
m3: 仅一个 create_user 函数
m4: 仅一个 GET /users 路由

✅ 好：
m1: 数据库连接 + ORM 基类（2个文件）
m2: 用户模型 + 用户服务（3个文件）
m3: 用户 API 路由（2个文件）
```

### 反面2：循环依赖

```
❌ 不好：
m1 依赖 m2，m2 依赖 m1 → 循环！

✅ 好：
提取公共部分到 m0，m1 和 m2 都依赖 m0
或：合并 m1 和 m2 为一个模块
```

### 反面3：按文件类型拆分

```
❌ 不好：
m1: 所有 models
m2: 所有 services
m3: 所有 routes

✅ 好：
m1: 用户（model + service + route）
m2: 订单（model + service + route）
```

按文件类型拆（所有 model 在一起）看似整齐，但修改一个功能要跨多个模块，违背了"高内聚低耦合"原则。

## 拆分自检清单

在最终确定架构前，逐项检查：

- [ ] 每个模块是否只有一个明确的职责？
- [ ] 每个模块是否有清晰的对外接口（导出）？
- [ ] 依赖关系是否单向无环（DAG）？
- [ ] 每个模块是否能独立测试？
- [ ] 每个模块的文件数是否在 1-5 个？
- [ ] 有没有模块预计少于 50 行代码？
- [ ] 修改一个业务功能时，是否只影响少数模块？
