# ADR-0002：F+B+C 强制执行机制（从文本约束到工具化检查点）

- 状态：已采纳（rwgj v1.1）
- 日期：2026-08-04（记录）

## 背景

早期版本完全依赖文本规则约束 LLM：要求"必须填写模块详情""必须校验一致性"。
实践反复证明 LLM 执行是概率性的——会遗忘规则、走捷径、跳过整层，且"既是运动员又是裁判"，
自我声明完成不可信。ENFORCEMENT-GUIDE.md 记录了大量"智能体不完整调用"现象。

## 决策

从"教 LLM 该怎么做"转向"让 LLM 做不到就走不下去"，三件套互补：

- **F（占位符）**：模板必填字段放 `__待填__`，缺失可见；`check_placeholders.py` 未清空返回错误码 1。
- **B（状态文件）**：`manage_state.py` 客观记录 9 个必需阶段完成度，完成判断从 LLM 主观变成文件客观。
- **C（事中裁判）**：`judge_progress.py` 综合三重检查给出 `can_proceed` 裁决，不通过禁止继续。

配套：`detect_should_trigger.py` 强制触发检测 + `gate_check.py` 收尾门禁 + 主会话可见回执。

## 后果

- ✅ 关键完整性由工具强制，LLM 只能"填对"或"被拦截"，不能"假装完成"。
- ✅ 返回码契约（0/1）+ `--json` 机器可读输出，可接入 CI/自动化。
- ⚠️ 工具链本身成为信任点——因此本仓库配套了自检锚点（verify-all.sh）、单元测试与文档数字对账，防止裁判失职。
- ⚠️ 摩擦增加：每阶段都要跑命令更新状态；这是换取完整性的刻意代价。
