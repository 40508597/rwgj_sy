# 实现任务规划

在需求与架构落位足够明确、需要把多步变更交给自己或其他执行者时使用。小修复可以只保留一项可验证任务。
输入：已确认需求、模块/接口编号、当前代码、约束和真实工具条件。
产出：按依赖顺序组织的任务，每项有输入、输出、具体修改范围、可观察验收与恢复位置。

## 规划方法
- 按可以独立实现、验证或拒绝的交付拆任务；步骤短不等于任务有价值。每项说明完成后哪个行为发生变化。
- 对跨任务依赖登记消费与产出的接口：名称、参数/字段、错误和状态语义。后续任务引用的签名必须与前序一致。
- 区分已有事实、待实现结果和待确认选择。保持用户硬约束原样可追溯，不用预计接口假装已经存在。
- 文件清单说明新增、修改和测试的责任；不能用同名目录代替具体范围，也不固定目录结构或编程语言。
- 验证步骤写可在当前环境执行的命令/操作及预期结果；未具备工具时记录缺口，不编造退出码。
- 检查任务拓扑、循环依赖、共同写入文件和合并条件；共享状态有单一归属，冲突先回到模块设计处理。
- 只在任务确实需要时使用测试先行、并行执行或隔离工作区。提交频率与执行方式服从用户授权和项目惯例。
- 计划完成后自行核对需求覆盖、边界、签名引用、验证责任和未解决项；有现成授权便继续允许的工作。

## 回写与证据
任务与文件责任写入 `/实现清单`，契约写入 `/完整细节`，验收归入 `/测试责任矩阵`，继续位置归入 `/上下文恢复点`。
计划审查属于 review；没有实际运行不能写 execution 通过。计划变化要重新绑定当前语境和输入，保留已失败/未验证项。
参考原文中的每任务提交、固定模板路径、Superpowers 专属执行器和重复审批不属于本适配流程。
