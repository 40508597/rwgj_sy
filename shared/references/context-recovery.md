# 上下文压缩恢复协议

## 权威位置与目的

项目总架构、模块记录和恢复点保存连续开发所需的事实，支持对话压缩、会话中断、换模型和换执行者。长期决策及理由留在拥有它们的架构记录；恢复点只保留下一轮继续所需的目标、约束、状态、位置和证据引用。

递归布局从根 `architecture.json` 沿 `模块路由` 进入；既有集中布局跟随 `指向`。恢复点在根当前事实或明确登记的任务记录中维护一份。模块可以保留本模块交接信息，根引用其编号、路径和状态，不在每个祖先抄录细节。项目状态不写全局技能目录。

## 何时更新

架构或实现变化、测试结果、阻塞/未验证项、用户约束改变了续跑事实时更新；同一批次合并写入。每轮结束及停止、等待或跨会话前核对恢复点是否仍准确，未变化无需重写同一段。纯只读/完全跳过任务不为记录流程新建状态。

## 最小记录示例

核心字段与类型以 schema 为准，按实际需要补相关路由、基准版本、正在进行的模块和已确认约束：

```json
{
  "上下文恢复点": {
    "当前任务": "本轮已确认目标",
    "当前阶段": "实现",
    "继续位置": "modules/accounts/architecture.json 的当前行为节点",
    "最近完成": ["已确认并完成的事实"],
    "下一步": ["核对当前版本后继续未完成的可执行动作"],
    "已触碰文件": ["modules/accounts/service.src"],
    "用户明确约束": ["保留原约束；没有额外约束时可为空数组"],
    "未验证项": ["见 architecture/evidence/current.json 的未验证项"],
    "剩余风险": ["影响续跑的风险摘要及权威记录位置"]
  }
}
```

`已运行命令`可引用实际收据；错误全文、截图清单和测试输出留在验证证据产物。用户明确不要的内容必须在约束或其权威引用中保留，不能由功能展开重新纳入。需要基准版本时记录提交、文件摘要或其他可核对版本，不用模糊的“最新版”。

## 恢复流程

动手前能否具体说出“当前任务 / 当前阶段 / 下一步”？任一答不出先恢复，不依赖压缩通知。

1. 读根 `architecture.json`，确认模块路由或集中指针与登记入口。
2. 读权威恢复点/任务记录和已有 `architecture/_state.json` 阶段进度；集中布局的任务切片按清单定位。缺失时报告并核对实际事实，不当作已完成。
3. 核对目标、用户约束与有效决策，进入相关模块取得契约、源码、测试和必要消费者，不全量重读项目。
4. 核对基准版本、已触碰文件、当前父入口与差异，区分其他执行者修改、未登记工作和过期证据。
5. 从有效下一步继续；事实冲突先按 `/校验架构` 分类，不从头重新设计。

批准的计划不等于已有实现，历史通过不等于当前版本通过。继续已接受决策；需求、约束或证据改变时才重评并说明原因。跨执行者接力按需读 [交接完整性](handoff-integrity.md)，原约束、ID、未完成与部分失败不能被摘要丢失。

## 收尾与边界

完成后仍保留可识别的当前任务、阶段、继续位置和下一步。可如实记录“本次完成，无待办”，指向最终证据；这不是新的实施任务或定时复核授权。

恢复点保存事实、下一步、用户明确不要、未验证项与剩余风险；详细内容有权威位置时引用，不复制全部历史、失败全文或长篇对话。关键续跑事实写入项目，不能只留最终回复。路由/归属/职责/共同契约变化时同步相关入口；普通局部修改无需机械重写全部祖先。
