# 多层递进设计（分层输出）

**核心问题：一次思维过程中同时思考 10+ 个模块，思考深度必然被稀释。**

**解决方案：分层输出。每一层只聚焦一个层面，前一层结论锁定后作为下一层的输入前提。这不是多次 API 调用，而是 Agent 在单次执行中将思维过程分层推进。**

### 四层递进

四层描述设计阶段与信息深度，不限制模块目录的递归层数。新项目根 `architecture.json` 保存真实总架构，沿模块目录中的架构与直接子路由逐层深入；已有集中布局仍跟随根指向与切片登记。物理组织见 [递归模块协议](recursive-modules.md)。

```
全景分析层：商业化全景分析
  聚焦："这个项目按商业标准应该是什么样"
  输出：项目类型、技术栈推荐、五大维度初稿、补全清单
  ↓ 结论锁定

拆块与骨架层：拆块 + 骨架设计
  聚焦："怎么拆块 + 基础设施怎么定义"
  输入：全景分析层的结论
  输出：拆块清单（含优先级和依赖）+ 根总架构、真实模块目录与本模块架构骨架
  ↓ 结论锁定

逐块深度设计层：逐块深度设计
  聚焦：每次只关注"一个块的完整细节"
  输入：架构骨架 + 相关契约摘要（签名、语义、错误、数据约束、消费者与变更依据）+ 当前块要求
  输出：当前块完整设计（接口/异常/测试/数据表/组件树）+ 更新事实所属架构 + 代码 + 测试
  ↓ 自动进入下一块

集成验证层：集成验证
  聚焦："接口一致性、依赖完整性、跨模块矛盾"
  输出：验证报告 + 修复建议
```

### 层间信息传递

层间传递可核对的结论、决策理由、约束、未决项与证据位置，不复制全部讨论。下一层依据当前有效结论继续推进；需求、约束或证据变化时重新评估受影响决定并记录原因，不能把早期结论永久冻结。

### 项目架构的四层信息结构

**核心问题**：扁平 JSON 把所有信息堆在同一层级——路由、接口签名、组件树、数据库字段全混在一起。AI 做任何任务都要吞下全部细节，导致"东一块西一块"——它无法区分"全局骨架"和"局部细节"。

**解决方案**：按以下四种信息深度组织项目架构。先读根目标、约束和路由，再沿相关模块逐层进入、取得本次需要的语义与实现细节；目录可继续递归，任意一层模块可有实现。已有集中布局从 `architecture/index.json` 与登记切片取得同样的信息，不改变既有入口：

```
第1层：项目骨架          第1次读取（任何操作的第一步）
  ├── 项目身份（类型/语言/框架）
  ├── 运行形态（Web/后端/桌面/移动/CLI/SDK/容器/插件等）
  ├── 入口结构（用户入口/接口入口/命令入口/事件入口/系统入口/资源入口）
  ├── 交付物（网页、服务、EXE/安装包、移动安装包、Docker镜像、SDK包、插件包等）
  ├── 系统集成（托盘、通知、文件关联、本地协议、权限、自动更新等）
  ├── 模块拓扑（节点列表+依赖图，只有名称和关系）
  ├── 模块树（父模块/子模块/叶子模块/落位）
  ├── 模块详情（职责/非职责/内部结构/状态机/数据责任/错误边界）
  ├── 页面拓扑（页面列表+依赖的模块）
  └── 数据拓扑（表列表+所属模块）
  → AI 读完就知道"项目有哪些运行形态、入口在哪、交付物和系统集成是什么、谁依赖谁、谁包含谁、每个模块负责什么/不负责什么"
  → 加新功能时，先据此判断候选归属，再核对相关契约、状态、数据与消费者后确定落位

第2层：接口契约          需要调用已有模块时读取
  ├── 每个模块的导出契约（名称+参数/返回+行为语义+错误+数据约束）
  ├── 每个模块的依赖声明（依赖谁+使用哪些接口）和相关消费者
  └── 关键版本、变更依据与验证证据位置
  → AI 知道"能调用什么、怎么调用、会出什么错"
  → 写新模块代码时先读必要契约；涉及行为、生命周期、共享状态或兼容性时继续读取相关细节与实际源码

第3层：实现清单          开始写具体模块代码时读取
  ├── 每个模块的文件列表（路径+说明）
  ├── 每张数据库表定义（字段/约束/索引/迁移路径）
  └── 每个页面的组件树骨架（组件名+嵌套关系）
  → AI 知道"要创建哪些文件、每个文件写什么"

第4层：完整细节          写具体函数/组件代码或调试时读取
  ├── 每个接口的完整参数说明+实现约束+测试用例
  ├── 每个组件的属性列表+交互事件链+五态展示
  └── 每个页面的布局+接口调用时序
  → 为实现提供足够依据；发现语义或验证缺口时局部回展开，先补所属架构再继续

关键规则：永远不要一次性把第4层的全部内容喂给 AI。
只传当前任务相关模块的第4层。
```

**防越层规则**（硬约束）：

使用项目架构时（修改/编码/调试），AI 必须：
1. **先声明**：本次任务需要读哪几层、哪些模块
2. **按实际影响读取**：编码 m6 时读取根约束、路由、本模块必要语义和实现、相关依赖契约与源码；行为变化影响消费者时补读相应契约、状态、测试和证据
3. **不得**以"了解项目全貌"为由读取无关模块的第4层细节
4. 如果发现需要额外信息，**再次声明补充读取**，而不是一次性全读

按需读取保护相关信息的理解深度，不省略必要的设计、消费者检查或验证；不得为了遵守预先读取范围而忽略新发现的影响。

完整字段说明见 [架构字段规范](schemas.md)。

## 分治设计法

大功能 → 拆小块清单 → 逐块深度设计 → 自动推进 → 集成验证。

### 单块设计标准

每块必须达到：**另一个不熟悉项目的开发者能独立写出完整代码。**

每块设计按四层信息深度写入拥有对应事实的根/模块架构；已有集中布局写入相应索引或切片：
- **第1层补充**：把当前块加入运行形态+入口+交付物+系统集成+模块拓扑+模块树+模块详情+依赖图+页面拓扑+数据拓扑
- **第2层完整**：当前块的导出接口完整签名、语义、错误与数据约束、依赖声明、相关消费者及变更/证据依据（不允许省略任何参数/异常）
- **第3层完整**：按实际职责确定文件列表、关联数据表DD、页面组件树骨架；文件数不设硬上限，需要时按独立职责继续拆为子模块
- **第4层完整**：每个接口的实现约束+测试用例、每个组件的属性/事件/五态
- **交互完整性检查**：设计完成后自动对照项目类型的检查包，逐项确认或补全，标注检查结果

### 模块详情标准

每个模块必须有 `模块详情`，用于约束模块内部工程边界。模块拓扑只回答“有哪些模块、谁依赖谁”，模块详情回答“这个模块负责什么、内部怎么组织、哪些边界不能越过”。

必填项：
- **职责**：模块必须承担的业务或技术责任。
- **非职责**：明确不属于该模块的内容，防止职责漂移。
- **所属功能树节点**：模块服务哪些功能树节点。
- **上游依赖 / 下游消费者**：依赖谁、被谁用、失败影响是什么。
- **内部结构**：服务层、仓储层、模型、工具、组件、任务等内部分层。
- **状态机**：模块管理的对象有哪些状态和允许流转；无状态模块写“不适用”。
- **数据读写责任**：读写哪些表/文件/缓存/外部资源，允许哪些操作。
- **错误边界**：可能错误、触发条件、处理方式、对应测试。
- **配置项**：环境变量、配置来源、默认值、缺失处理。
- **日志审计**：必须记录什么，禁止记录什么。
- **安全边界**：权限、敏感数据、输入校验、泄露风险。
- **性能约束**：延迟、吞吐、索引、缓存、批量处理等约束；无性能要求写“不适用”。
- **测试责任**：正常、边界、异常、权限、性能或回归测试责任。

停止细化条件：
- 一个不熟悉项目的开发者能根据模块详情判断代码应该放在哪个文件、什么逻辑不该放进该模块。
- 模块的输入输出、依赖、数据责任和错误处理已经清楚。
- 继续细化会进入具体函数实现步骤，应转入第2-4层。

### 模块树标准

每个中大型项目应有完整的模块包含视图，用于表达父子归属和颗粒度；模块依赖图表达消费关系，两者不能混用。递归布局可直接从路由派生包含视图，不要求手写第二棵树。

递归布局的真实父子归属以各层 `模块路由` 为权威，`模块目录` 与画布中的包含树从路由派生，不另行手工维护全树。`模块树` 缺失或为空时由路由派生；显式非空字段作为补充分组记录保留，不覆盖实际目录归属。集中布局仍由登记的关系事实持有包含树。以下字段说明完整概念视图，不要求每份模块文件重复登记全局父子关系。

完整概念视图中的节点应能回答以下信息；派生字段无需重复人工填写：
- **编号**：稳定编号，子模块可用 `父模块.子模块` 形式，如 `m6.session`。
- **名称**：真实模块名、目录名或领域名。
- **层级**：系统层 / 领域模块 / 子模块 / 叶子模块 / 内部单元。
- **父模块**：根模块写 `null` 或“不适用”；子模块必须指向真实父节点。
- **子模块**：数组；没有子模块也要写空数组。
- **职责**：该节点承担的责任，不能只写“同父模块”。
- **落位**：至少指向文件、接口、数据、页面或测试中的一种。

继续拆子模块的条件（满足任一即可）：
- 一个模块内部已经有明显不同的责任域、状态机或数据所有权。
- 模块文件数、组件数或接口数超过单块大小，继续由一个模块详情承载会变模糊。
- 某个内部能力会被其他模块直接调用，或需要独立测试/独立验收。
- 用户的模糊需求展开后，天然包含多个子流程、异常路径或角色视角。

停止拆子模块的条件：
- 叶子模块已有独立职责、文件/接口/测试落位，后续再拆只会进入函数级步骤。
- 子模块之间高度耦合，拆开会制造循环依赖或伪边界。
- 该节点只是私有辅助函数、常量或极小工具，不需要架构级追踪。

### 块的大小控制

| 项目类型 | 一个块大约等于 |
|---------|--------------|
| 后端 | 1个职责清楚的模块 + 实际关联数据结构与完整验证责任 |
| 前端 | 1个页面或独立交互能力 + 完整组件树与状态/异常/验收 |
| 全栈 | 1个后端模块 + 1个对应前端页面 |
| CLI | 1个命令 + 参数/选项/错误码 |
| 客户端/插件 | 1个用户入口或系统集成能力 + 生命周期/权限/错误恢复 |
| 交付物 | 1个目标平台构建产物 + 启动/安装/发布/卸载/更新验证 |

### 拆块原则

```
✅ 好："用户管理系统" → ①数据库连接 ②用户模型+表 ③CRUD服务 ④接口入口 ⑤登录入口 ⑥管理入口
❌ 差："用户管理系统" → ①所有后端 ②所有前端（太大了）
```
