# 架构布局与 JSON 切片协议

新项目默认采用 [递归模块架构](recursive-modules.md)：根 `architecture.json` 是真实总架构，每个受管模块目录有本模块 `architecture.json`。本文件规定既有集中切片布局的登记、加载与维护。两个布局服务于同一项原则：每项事实只有一个权威维护位置，按需读取，合成结果只读。

## 入口辨认

1. 根含 `模块路由`：读取根总架构，再沿相关子模块入口逐层定位；不套用根仅指针的规定。
2. 根含 `指向`：跟随登记的总索引，标准集中位置为 `architecture/index.json`。
3. 只有 `architecture/`：检查 `architecture/index.json`；不存在时报告缺少有效入口，不能只凭目录存在认定架构可用。

既有项目维持当前有效布局，不因工具升级移动源码。迁移需要显式设计归属、保持事实与引用、验证结果；不能让根总架构、模块文件和集中切片分别维护同一份事实。

## 集中切片布局

```text
architecture.json              # 轻量指针，仅适用于本布局
architecture/
  index.json                   # 项目身份、全局约束、摘要与切片登记
  _state.json                  # 全局阶段进度
  features/
    f_accounts.json
  modules/
    structure.json             # 登记的全局模块关系
    m_accounts.json
  data/
  pages/
  tasks/
    state.json                 # 恢复点、未决事项与任务变更
  quality/                     # 独立规则、事实与执行收据
```

集中布局的切片均放在 `architecture/` 内，不能将未登记的散落 JSON 当成权威；递归布局的模块架构按 `模块路由` 登记在真实模块目录，不受这一集中目录规则限制。`architecture/_state.json` 与 `architecture/quality/` 不作为业务架构切片登记，其他未知 JSON 仍需反向对账。

如明确采用集中布局，实际生成使用带占位符模板；空值目录样张仅供查看：

```text
python "<init_architecture_path>" --mode init --output "<项目根>"
python "<manage_state_path>" init --project-name "项目名称" --state-path "<项目根>/architecture/_state.json"
```

## 总索引与切片登记

集中根入口的权威指针字段为 `指向`，最小示例：

```json
{
  "指向": "architecture/index.json",
  "说明": "本项目使用集中切片，从总索引进入相关事实文件"
}
```

`architecture/index.json` 登记全局关系、局部事实和易变任务状态的位置。完整局部事实在相应切片中；根不再抄录一份完整模块详情或依赖图。

```json
{
  "架构切片": {
    "启用": true,
    "架构模式": "架构文件夹",
    "总索引文件": "architecture/index.json",
    "根入口文件": "architecture.json",
    "切片目录": "architecture/",
    "切片清单": [
      {
        "编号": "m_accounts",
        "类型": "模块",
        "路径": "architecture/modules/m_accounts.json",
        "包含": ["模块详情", "接口契约", "实现清单", "完整细节", "测试责任矩阵"],
        "状态": "进行中",
        "更新时间": "2026-10-09T00:00:00+08:00"
      }
    ]
  }
}
```

字段名使用中文；实际文件路径、语言标识符、接口签名、表名和数据字段保留原样。`包含` 显式列出切片提供的顶层业务字段，加载器拒绝超出声明范围的字段。

## 事实边界与同步

| 事实类型 | 权威内容 | 需要引用的其他事实 |
|----------|----------|--------------------|
| 功能 | 功能树子树、验收、异常与落位 | 实现模块和测试责任 |
| 模块 | 本模块详情、接口、实现清单与局部细节 | 功能、数据与依赖方契约 |
| 全局关系 | 模块包含与跨模块依赖；标准集中位置为 `modules/structure.json` | 各模块真实编号与接口 |
| 页面 | 组件、交互状态与界面验收 | 业务模块与数据契约 |
| 数据 | 结构、约束、迁移和读写归属 | 生产者与消费者 |
| 任务 | 当前目标、进度、未决、恢复与本次变更 | 相关事实路径及证据 |

每次修改权威事实，更新相关任务变更记录；仅在路由摘要、归属、契约或全局关系变化时更新相关上层登记。局部实现变更不机械重写全部祖先。删除或移动时在同一变更批次维护入口、引用和文件，完成检查前不宣称路由有效。当前事实、待实施设计和历史记录分别标明。

冲突先走 `/校验架构` 分类，结合源码、需求和版本依据裁决，不凭直觉选择一个覆盖另一个。各模块记录局部依赖即可；项目全局图由指定权威关系记录或工具合成，不在每个模块重复维护。 声明形式和消费者→提供方方向沿用 [统一关系规则](recursive-modules.md#包含关系与依赖声明)，集中布局保留已登记权威位置。

## 加载与合成契约

切片清单路径必须位于项目根内。启用且登记的文件为权威；缺失、不可读或越界是输入错误，不回退到旧缓存。切片不得修改 `指向`、`架构切片` 等加载配置。

有 `包含` 时，实际业务字段不可越过声明列表；编号、类型和更新时间等元数据不进入业务视图。既有清单未声明 `包含` 时，加载器从实际业务字段推导；新清单显式声明。

同一顶层业务字段，首个权威切片替换索引缓存；后续递归合并字典，带 `编号` 的数组按编号合并，无编号数组去重。不同模块键可并存，同一位置冲突值为输入错误，不采用最后覆盖。合成发生在工具内存中，不回写为另一份完整总索引。

## 按需读取与恢复

从根进入，读取全局目标、约束和路由，再取得本次相关事实。涉及跨模块时读取必要的关系与契约；定位后核对实际源码和测试。按需读取控制无关上下文，不削减需求展开、必要设计或验证。

恢复先读取项目状态和恢复点，再沿当前模块路径继续，核对已触碰文件、版本和未验证事项。不要因恢复全量加载历史，也不要跳过有效决策重新设计。详细规则见 [上下文恢复](context-recovery.md)。

## 迁移与归档

已有未分片 JSON 可以作为现状纳管输入。明确采用集中布局时，备份后使用 `init_architecture.py --mode migrate --from <输入> --output <项目根>`，逐域核对抽出的事实、根指针和登记，运行解析、占位符、一致性、影响与适用测试；记录范围和剩余风险。

转换为递归模块布局时，先确定真实模块目录和唯一归属，再逐块迁移架构记录与引用；源码只有在职责重构需要时才移动。两个布局不能独立持有同一事实。完成前比较迁移前后事实与证据，防止转换丢失信息。

历史原文件或合成快照可以存入明确的归档位置，标明版本与时间，不能替代当前入口。图纸同样从当前权威事实派生，不另建独立真相源；完整阅读规则见 [项目架构可视化](architecture-visualization.md)。
