# 快速上手：3 步开始

## 先判断是否该用

本技能用于中大型商业项目、长期维护项目、多模块系统和 AI 难以稳定维护的复杂代码库。一次性脚本、小 demo、临时实验、小型原型不调用本技能，直接让编程智能体处理即可。

## 第1步：创建项目骨架

在对话中输入：

```
/创建架构

我想做一个[你的项目描述]，比如：
- "用户管理系统，支持注册登录、角色权限、数据看板"
- "一个 CLI 工具，批量转换图片格式并压缩"
- "一个桌面便签应用，支持分类和搜索"
```

AI 会自动完成全景分析 + 功能树建模 + 专业能力索引匹配 + 拆块 + 骨架设计，建立根总架构 `architecture.json`、真实模块目录、各模块的 `architecture.json` 与拆块清单。模块可继续包含子模块；源码与测试按照责任归属登记。

创建时，AI 不只是列功能，而是按三段式展开：

1. 需求语义展开：把模糊需求展开为应有功能域
2. 功能本体展开：把每个功能名天然绑定的子功能、状态、交互、异常补齐
3. 功能树建模：把功能递归拆到可验收、可落位、可测试的叶子节点
4. 专业能力索引匹配：判断是否需要 UI、测试、安全、性能、部署、文档等已有技能辅助
5. 架构落位展开：把功能落到模块、入口、接口、数据、页面、测试和变更记录

所需时间由需求清晰度、模块规模和验证范围决定；不以演示规模估计真实项目耗时。

## 第2步：看 AI 自动逐块推进

骨架生成后，AI 自动从第1块开始，逐块深度设计 → 写代码 → 测试。你不需要逐块确认，AI 会自动推进直到所有块完成。

逐块耗时取决于实现复杂度、项目运行环境与实际验证结果；遇到阻塞时保留真实进度。

**如果中途中断**：重新打开对话，输入 `/追加架构 [块名]` 继续。

## 第3步：日常使用

项目建好后，日常开发常用这些入口：

| 场景 | 命令 | 示例 |
|------|------|------|
| 加新功能 | `/追加架构` | `/追加架构 加一个评论功能` |
| 改已有功能 | `/修改架构` | `/修改架构 users 表加 phone 字段` |
| 查漂移 | `/校验架构` | `/校验架构 检查代码和 architecture/ 架构文件夹是否一致` |
| 修 Bug | 直接描述 | `登录时密码错误没有提示，帮我修` |

**使用方式**：可以直接描述需求，AI 自动选择新增、修改或校验；无需记忆命令。纯问答和查看走轻量路径，受管项目的小改动只定位受影响功能簇。

## 日常修改的最短路径

1. **定位**：读取根 `architecture.json`，用 `module_architecture.py route --architecture <根架构> --file <项目相对源码路径>` 找到所属模块；只读相关路线的模块职责、契约、源码与测试。未知文件先用 `search` 找职责，不盲目全量读取。
2. **修改**：先更新拥有本次事实的模块架构；接口有变化时沿 `impact --direction both` 核对实际依赖与消费者，再修改代码、运行针对性测试。既有设计已覆盖时只补本次差异与证据。
3. **核验**：更新当前证据后运行 `gate_check.py <项目根> --quality-required --json`。红线误报按 [通用质量协议](universal-quality.md) 记录有证据的语义复核；缺事实保持 unknown。按已检范围汇报结果。

上述工具先用 resolve_tool 解析路径。详细参数见 [命令速查](commands-cheatsheet.md)。这条路径减少无关资料，不削减相关设计、专业子能力和必要验证；文件读取数不是模型 token 节约证明。

## 项目架构文件是什么

项目自身保存的结构、语义与工作状态。新项目根 `architecture.json` 保存总体目标、约束与模块路由；每个模块目录有自己的架构文件，按需递归进入源码与测试。已有集中布局仍按原指针和切片读取。具体规则见 [递归模块](recursive-modules.md)。它告诉你：
- 项目有哪些模块、谁依赖谁（第1层）
- 每个模块提供什么接口、怎么调用（第2层）
- 每个模块有哪些文件、数据库有哪些表（第3层）
- 每个接口的详细参数、测试用例（第4层）
- 哪些功能树节点建议使用 UI、测试、安全、性能、部署、文档等专业能力
- 哪些测试、架构校验、浏览器验收、截图和未验证项能证明项目真的完成

**不需要你手动编辑** — AI 通过命令自动维护。你只需要知道它存在，以及"改代码前先改 JSON"这条铁律。

## 常见问题

**Q: 小项目也需要 architecture.json 吗？**
A: 如果是一次性脚本、小 demo、临时实验或没有长期维护预期的小型原型，不需要调用本技能。进入中大型商业项目或长期维护项目后，才使用随项目保存的根架构与模块架构作为事实依据；项目状态不写入全局技能目录。

**Q: 架构文件夹会不会过时？**
A: 先更新架构再改代码能降低漂移风险，仍可能因漏登记、外部接口变化或建模错误而陈旧。按本次范围定期核验，发现偏差用 `/校验架构` 分类并同步；未验证范围应明确保留。

**Q: 我能手动编辑 JSON 吗？**
A: 可以，但建议用命令。模块工具提供局部更新及结构校验；AI 仍需检查行为影响、更新变更记录并运行真实验证。
# 长程项目工具链

从功能定位到架构/源码共同修改、真实验证及接力，可按需使用统一 `taskarch.py`：query → change begin/stage/preview/apply → 项目原生验证 → change verify/accept。协作、交接、暂停点、检查点与完整参数见 [项目工具链](./project-toolchain.md)。原有创建、纳管、质量和可视化操作继续适用；操作成功与验收通过分开表达。
