# 递归模块架构

本协议用于指导 AI 创建真实模块目录，并从项目根逐层定位、理解与修改项目。新项目默认采用此布局。已有集中切片项目继续按其入口与登记读取，规则见 [JSON 切片协议](json-sharding.md)。

## 职责与基本约束

- 根 `architecture.json` 是项目总架构，保留项目目标、全局约束、共同契约、总体路由及根自身的事实。模块架构跟随实际模块目录，每个受管模块一份本模块 `architecture.json`。
- 模块可包含任意数量的子模块，任意一层都可拥有源码与测试。没有固定层数上限；真实目录必然有限，按职责、数据归属、接口与验证边界决定深度。不把普通资源、构建或辅助目录自动认定为模块。
- 模块包含关系是一棵树；跨模块调用、数据和接口依赖另成图。父子包含不代表调用，依赖不改变目录归属。
- 每项事实由一个位置权威维护。上层路由只保留定位必需的职责摘要与入口，完整局部语义在所属模块；全局约束和共同契约明确归根或共同责任模块，其他模块引用。不逐层抄录下层全文。
- 目录、架构路由、编号与源码归属可确定检查；业务边界与方案适用性需要工程判断；实现和质量通过需要真实证据。工具合成索引与图纸只读，不产生第二份人工维护的真相源。
- 不限定实现语言、文件后缀、框架或 IDE，不以 AST、import 语法或某种编译器作为启用前提。语言工具在可用且适用时补充观察证据，缺少证据如实标记。

## 目录与路由示例

下面仅示范职责落位。实际文件名、模块数量和目录选择由项目决定；`.src` 代表项目自己的源码格式，不能照抄为特定语言要求。

```text
project/
  architecture.json
  application.src             # 根自身可以有实现
  tests/
  modules/
    accounts/
      architecture.json
      service.src             # 父模块可以有实现
      tests/
      sessions/
        architecture.json
        storage.src
        tests/
    workspace-ui/
      architecture.json
      window.src
      tests/
  architecture/
    _state.json               # 全局阶段进度
    quality/                  # 本次适用规则、事实、执行收据
```

根的路由字段示例；这是局部片段，完整根仍应按初始化模板填写其余项目架构字段：

```json
{
  "模块路由": {
    "版本": 1,
    "编号": "project",
    "名称": "项目",
    "职责": "组织账号能力与工作界面，提供完整应用入口",
    "子模块": [
      {
        "编号": "m_accounts",
        "路径": "modules/accounts/architecture.json",
        "职责": "管理账号身份与会话入口"
      },
      {
        "编号": "m_workspace_ui",
        "路径": "modules/workspace-ui/architecture.json",
        "职责": "提供工作界面、交互状态与用户反馈"
      }
    ]
  }
}
```

`modules/accounts/architecture.json` 中的路由：

```json
{
  "模块路由": {
    "版本": 1,
    "编号": "m_accounts",
    "名称": "账号",
    "职责": "管理账号身份与会话入口",
    "子模块": [
      {
        "编号": "m_sessions",
        "路径": "sessions/architecture.json",
        "职责": "维护会话创建、失效与撤销"
      }
    ]
  }
}
```

### 路径与归属

`模块路由.子模块[].路径` 相对**当前架构文件所在目录**解析，必须指向项目内真实后代模块目录的 `architecture.json`。编号在项目内唯一，父入口的编号与职责必须和子文件路由头一致。禁止自指、父子环、越界、重复挂载和把兄弟目录伪装成子模块。

源码、测试、迁移等事实中的文件路径统一相对**项目根**。例如 `m_accounts` 的清单登记 `modules/accounts/service.src`，`m_sessions` 登记 `modules/accounts/sessions/storage.src`。父模块不占有已属于子模块目录的文件，也不把兄弟或外部文件登记为自己的实现。跨模块测试可由根或共同责任模块持有，并引用受测模块；位置与归属应明确。

已有目录纳管使用 `add --adopt-existing` 明确选择：目标目录必须已经存在，且没有 `architecture.json`，工具新增模块记录与父入口，不移动或改写现有源码。先依据实际代码确定职责、契约与归属，纳管后的骨架仍需补齐设计与验证。未指定该选项时，`add` 面向新目录，遇到已存在目标拒绝覆盖。

稳定编号表达模块身份，路径表达当前落位。移动或拆分时保留可追踪身份，维护父入口、引用、源码清单和证据；不同模块不能复用编号来掩盖职责变更。发现未登记的模块架构或源码归属冲突时先检查，不依据目录名字自动补成已批准设计。

## 本模块需要说明什么

沿用 [架构字段规范](schemas.md) 的设计能力和模块详情底线。模块记录按自己的编号维护 `模块详情`、`接口契约`、`实现清单`、`完整细节` 等相关事实；不在子文件定义其他模块的完整详情或实现清单。

递归布局的本层 `模块详情`、`实现清单` 字典键及记录内显式 `模块编号` / `模块号` 必须与本层路由编号一致；多个编号别名不能互相矛盾。源码责任由实际路由与登记决定，不以记录内另一个编号转移归属。集中布局的显示名称键与稳定编号是不同概念，继续按其既有合同读取。

字典型合成容器按稳定对象编号区分事实。例如账号模块的细节写为 `"完整细节": {"m_accounts": {"测试用例": ["缺少必需字段时拒绝创建"]}}`，会话模块使用自己的 `m_sessions` 键；不要在多个模块都把 `测试用例` 直接放在 `完整细节` 第一层，造成同一全局键声明不同值。共享事实保留一个权威位置，其他模块引用；发现冲突先核对归属，不以写入顺序覆盖。

| 内容 | 需要回答的问题 |
|------|----------------|
| 职责与边界 | 为什么有这个模块，负责什么、不负责什么，对应哪些已确认功能？ |
| 行为与生命周期 | 输入、输出、状态流转、边界、失败、恢复和适用交互反馈是什么？ |
| 契约与依赖 | 导出什么，调用谁的什么接口，哪些消费者受本次修改影响？ |
| 数据与实现 | 状态/数据由谁拥有，哪些源码、测试和配置归本模块？ |
| 质量与验证 | 关键约束怎样检查，哪些已实测、未验证或已过期？ |
| 路由与接力 | 子模块各负责什么，当前工作到哪里、依据何在、下一步是什么？ |

模块详情仍保留职责、非职责、所属功能树节点、上游依赖、下游消费者、内部结构、状态机、数据读写责任、错误边界、配置、日志审计、安全、性能与测试责任。按实际需要写内容或明确不适用，不用占位文本制造完整假象。UI、规划、架构、测试、安全等专业能力继续按 [专业能力索引](capability-index.md) 动态选择与实际加载。

当前有效事实、待实施设计与历史记录分别标明。新架构中刚添加的模块或验收计划不代表已有代码，记录过的测试命令也不代表本次运行通过。决策保留驱动、候选、取舍、验证方式与重新评估条件；历史证据保留对应版本和范围。

### 本模块功能树

功能树完整语义由拥有它的根或模块维护：根保存跨模块目标、取舍与必要导航，模块保存本地操作的输入/前置、行为、状态、异常、验收与架构落位。子模块可以直接有 `功能树`，不要求把全部叶子写回根；`所属功能树节点`用于关联已确认节点，不能代替节点自身语义。

工具按稳定 `编号` 合成功能树片段。子模块片段需要连接已有功能祖先时，只保留祖先编号与通往本地节点的子节点路径；本地完整节点在所属模块写一份，不抄其他分支。相同编号的字典/子节点可合并，冲突标量拒绝覆盖；合成顺序不作为业务顺序承诺。完整合成仅用于校验、查询和图纸，修改仍回到权威模块文件。

三层示例见 [recursive-local-features](../assets/examples/recursive-local-features/architecture.json)，沿 orders → rules 读取局部节点；示例明确无业务实现和执行证据，结构可读不代表交付通过。

### 包含关系与依赖声明

`模块目录`始终从实际路由派生，表示物理父子与源码归属。递归布局的 `模块树` 缺失或为空时由路由派生包含视图；显式非空树保留补充分组与扩展属性，不覆盖物理归属。无需手写第二棵完整目录树。

模块依赖图统一为**消费者 → 提供方**，与包含树分开。现有 `模块拓扑.依赖图`、`实现清单.<模块>.依赖模块`、`模块详情.<模块>.上游依赖/下游消费者` 声明由同一收集器解释，并保留文件/JSON Pointer来源。同一边的多份历史声明合为一边，保留全部来源；它们是声明，不是实际源码依赖观察。非法记录不能算完整图，未知模块仍需核对；父子包含不能推断调用。

根架构若已登记集中切片，合成视图中的依赖仍追溯到实际声明文件、原始 JSON Pointer 和文件 SHA256，而非合成后的根位置。该来源只用于内存查询、影响分析与图纸，不新增第二份业务真相源；修改回到该物理位置，再重新加载并核验。

新增关系选择所属模块的一处权威事实维护，不要求四种形式同时填相同边。14项详情中的相关维度可以用 `{ "说明": "见本模块实现清单的依赖模块或反向关系查询" }` 表明引用；说明性对象不形成额外边。具体调用的签名、错误和消费者仍在接口契约维护并核对。真实代码关系由工程原生采集器和通用质量协议观察，不能用声明图代替实测。

### 根级字段与模块局部记录

递归布局中，下列精确键保留为根级字段，子模块架构的顶层不得使用；归属以 `shared/scripts/_module_tree.py` 的 `GLOBAL_FIELDS` 为准。此表说明字段归属，不要求根新增全部字段。

| 根级范围 | 保留的顶层键 |
|---|---|
| 项目与入口 | `项目`、`指向`、`架构切片`、`索引摘要`、`项目身份` |
| 全局接力与变更 | `上下文恢复点`、`未决问题`、`变更记录` |
| 全局验证与质量 | `验证证据`、`质量状态`、`质量规则`、`质量门禁`、`质量策略`、`质量事实`、`全局质量状态` |
| 专业能力计划与使用 | `专业能力索引`、`专业能力调用`、`能力调用记录` |
| 全局扫描范围 | `扫描忽略目录` |

模块自己的变更、待办、接力信息与证据索引可复用已有模块工作状态，或使用自定义局部字段，例如 `局部变更记录`、`局部验证索引`；这些是示例键名，不是新增必需字段。它们保留在所属模块，并由合成视图的 `模块归属事实` 按模块编号呈现。全局记录引用模块文件与必要的 JSON Pointer，局部记录引用实际证据产物；同一详情维护一份，不复制全局计划或把换名当作规避归属。

`扫描忽略目录` 也不得在子文件的 `模块路由` 中重新定义；派生的 `模块目录`、`模块归属事实` 由工具生成，不写入架构输入。既有集中布局仍按总索引与登记切片读取，不能把集中切片的字段落位直接套到递归子模块。

模块可以使用自定义局部字段保存接手信息，例如在 `m_sessions` 的文件中记录：

```json
{
  "局部工作状态": {
    "任务": "补齐会话撤销后的拒绝访问行为",
    "阶段": "实现中",
    "下一步": ["补充撤销后再次访问的测试", "运行本模块测试及账号集成回归"],
    "未验证项": ["账号入口调用撤销接口后的实际反馈"],
    "证据索引": ["architecture/quality/session-revocation-receipt.json"]
  }
}
```

这里只示范记录形式，证据索引指向实际产物才有依据。根 `上下文恢复点` 引用相关模块与继续路径；模块局部字段按上表保留在所属模块，不复制全局记录。

## 创建项目

1. 充分理解需求，按功能簇展开核心、天然绑定、适用商业标配、强相关衍生与关联功能，处理生命周期、异常、交互和验证责任。只对尚未裁决的关键边界澄清，不因读取预算、目录骨架或实现批次削减功能发现。
2. 比较必要方案，确定全局目标与约束、状态/数据归属、模块职责、共同契约、依赖和验收。按职责提出真实目录结构，不先按目录层数填业务。
3. 初始化真实根架构；为已确认职责建立模块目录与路由骨架。未完成细节保留为待设计，不把骨架或空目录标记已实现。
4. 沿功能与依赖顺序逐块深度设计，先更新拥有本次事实的架构，再实现与测试。发现新缺口时局部回展开，分类必须补、建议补、待确认或明确排除。
5. 检查接口协作、全局目标和适用质量，运行真实集成验证；保存结果、未验证项与恢复信息。

已确认契约可支持并行或使用替身推进，但依赖能力未完成时必须明确集成未验证，不能用模块自测替代整体验收。不强制每个任务使用多智能体，也不把模块永久绑定某个执行者。

## 从需求逐层找到源码

修改任务从根读取全局目标、约束和总体职责路由，沿相关分支逐层深入。必要时探索多个候选分支；一个功能跨多个模块时保留多条路径，确定主要模块与协作模块。

到达目标后读取本模块相关详情、接口、实现清单与验证责任，取得必要的上游契约、下游消费者和共同约束，再核对实际源码及测试。父模块持有的代码可以直接在该层修改，不要求所有任务落到叶子。

查不到适合的责任位置时先判断缺登记、路由过期、边界设计错误或确实新增职责；不得把新功能随意塞进名称最像的模块。架构与代码不一致先分类，再修复记录或实现。文件路径搜索可以辅助发现候选，但修改前仍确认根到目标的归属与契约路径。

局部读取只降低无关内容成本。涉及全局约束、共享数据或契约改变时必须扩展相关范围，不以“只读当前模块”为由遗漏关联能力或必要验证。

## 工具操作

工具通过 `resolve_tool.py module_architecture --json` 解析，保持工作目录为调用方项目。下面 `<module_architecture_path>` 是解析出的脚本绝对路径。路径含空格时一律加引号。

```text
python "<module_architecture_path>" init --output . --id project --name "项目名称" --responsibility "项目总体职责"
python "<module_architecture_path>" add --architecture architecture.json --parent project --directory modules/accounts --id m_accounts --name "账号" --responsibility "管理账号身份与会话入口"
python "<module_architecture_path>" add --architecture architecture.json --parent m_accounts --directory sessions --id m_sessions --name "会话" --responsibility "维护会话创建、失效与撤销"
python "<module_architecture_path>" read --architecture architecture.json
python "<module_architecture_path>" route --architecture architecture.json --module m_sessions
python "<module_architecture_path>" read --architecture modules/accounts/architecture.json --project-root .
python "<module_architecture_path>" read --architecture modules/accounts/sessions/architecture.json --project-root .
python "<module_architecture_path>" route --architecture architecture.json --file modules/accounts/sessions/storage.src
python "<module_architecture_path>" search --architecture architecture.json --query "会话失效"
python "<module_architecture_path>" impact --architecture architecture.json --module m_sessions --direction both
python "<module_architecture_path>" check --architecture architecture.json
```

已有目录显式纳管、排除项目中的架构样例或证据目录时，例如：

```text
python "<module_architecture_path>" add --architecture architecture.json --parent project --directory existing-component --id m_existing --name "既有组件" --responsibility "依据真实代码填写组件职责" --adopt-existing
python "<module_architecture_path>" check --architecture architecture.json --ignore-dir examples --ignore-dir evidence
```

- `read` 只读 `--architecture` 指定文件及其直接子入口，不自动展开后代。逐层读取子模块时显式传 `--project-root` 保持清单按项目根解释；按编号查找先用 `route` 得到路径再 `read`。`route` 的模块和文件选项互斥，文件路径相对项目根。
- `search` 提供候选，不能代替职责、契约和源码核对。`impact` 按已记录依赖列出相关方，未采集的动态调用和行为传播仍须专项检查，不能把结果当作完整证明。
- `check` 检查路由、身份、归属与事实结构；初始化骨架可通过路由检查而仍存在待填业务字段，完整交付继续运行占位符、一致性、漂移和质量门禁。
- 反向扫描把检查范围内未登记的 `architecture.json` 按命名约定视为潜在架构记录，不能因内容没有 `模块路由` 就静默跳过。默认排除系统、依赖与缓存目录；项目自己的样例、测试夹具或证据目录如需长期排除，在根 `模块路由.扫描忽略目录` 中声明项目相对目录数组，如 `["tests/fixtures", "architecture/evidence"]`。局部检查可用可重复的 `--ignore-dir NAME` 额外排除，输出保留实际范围；临时选项不改变后续门禁。共享扫描器在写入预检及完整门禁中读取根配置，子模块不能重新定义全局范围。排除只影响未登记架构盘点，不能豁免已登记模块、源码存在性或原有质量检查；忽略内容不计入已验证范围。
- `update` 使用 `--module`、`--patch` 和 `--expected-sha256` 精确更新本模块；先读取最新内容与摘要，准备变更，再以该摘要提交。`--patch` 指向 UTF-8 JSON 对象文件，按 JSON Merge Patch 递归修改：`null` 删除键，数组整体替换。只提交本次需要的字段；版本不一致时重读、核对并合并，不强行覆盖。工具在写前检查摘要并原子替换文件，属于乐观版本保护；共同文件仍须协调写入责任，不能把它当作完整并发事务。
- 读取或检查失败时报告具体缺口；不能静默回退到旧副本、空对象或凭记忆继续写入。

工具只处理结构化操作与检查，不替代架构判断、源码理解、真实运行或用户授权。合成业务视图保留全部事实及派生模块目录，供既有验证器与可视化使用；无需把全项目合成内容读入模型上下文。

局部更新示例：先读取目标返回的 `sha256`，将以下对象写成项目内的补丁文件；示例工作状态须替换为本次真实情况：

```json
{
  "局部工作状态": {
    "阶段": "测试中",
    "下一步": ["运行撤销后的账号入口集成回归"],
    "未验证项": ["实际入口调用链尚未运行"]
  }
}
```

```text
python "<module_architecture_path>" update --architecture architecture.json --module m_sessions --patch session-state-patch.json --expected-sha256 "<刚读取的64位摘要>"
```

扫描忽略项含 `/` 时精确匹配项目相对目录；单个目录名称会排除各层同名目录。优先采用 `tests/fixtures` 这类具体路径，并核对输出范围。

父路由与子模块头的职责必须保持一致。变更此类跨文件事实时，先分别读取所有涉及文件及其摘要，再将协调补丁放在同一个 UTF-8 JSON 文件中；`补丁` 仍使用上述 Merge Patch 规则：

```json
{
  "更新": [
    {"编号": "m_accounts", "预期SHA256": "<账号架构的64位摘要>", "补丁": {"模块路由": {"子模块": [{"编号": "m_sessions", "路径": "sessions/architecture.json", "职责": "新的已确认职责"}]}}},
    {"编号": "m_sessions", "预期SHA256": "<会话架构的64位摘要>", "补丁": {"模块路由": {"职责": "新的已确认职责"}, "模块详情": {"m_sessions": {"职责": "新的已确认职责"}}}}
  ]
}
```

```text
python "<module_architecture_path>" update-batch --architecture architecture.json --patch coordinated-patch.json
```

数组整体替换，准备父路由补丁时保留所有未改变的兄弟入口。批量操作先校验全部摘要及候选树，任一摘要过期或结构冲突都不开始写入；串行落盘失败时尽力还原本次已写且未被他人修改的文件。它仍是乐观更新，进程崩溃、多执行者无协调写入不具备强事务保证；共同文件应约定单一写入责任，恢复后核对实际差异再继续。工具更新完成后还须检查职责、契约、测试和证据等语义事实是否同步。

## 修改、协作与验证

修改前确认变更属于职责、契约、数据、行为或内部实现哪一类，查阅消费者并决定实际影响范围。接口签名没变也可能改变行为、错误、性能或状态语义，不能自动认定下游不受影响。

先更新所属事实与本次变更依据，再改代码；必要时同步契约生产者和消费者。只有子模块职责、入口、共同契约或全局约束变化时才更新相关上层；普通局部修改不逐层改写全部祖先。跨模块执行分工约定临时责任、可写文件和共同文件的协调方式，不按角色身份替代证据。

每个批次验证受影响的真实行为，完整交付运行既有 `gate_check.py <项目根> --quality-required --json`。质量规则按 [通用质量](universal-quality.md) 配置事实与执行收据；模块路由检查通过不能代替代码质量、界面验收或集成测试通过。

改动后更新当前有效事实、适用证据与最小恢复点：当前目标和阶段、相关模块编号及路径、已经成立的决策、触碰文件、未解决问题、未验证项和下一步。恢复时先核对版本和实际差异，再继续；详细见 [上下文恢复](context-recovery.md) 与 [交接完整性](handoff-integrity.md)。

## 可视化与长期维护

项目视图从同一套当前事实派生，展示根目标、模块目录、职责、接口、跨模块依赖、流程、源码位置与验证状态；由总览逐层深入，不能因布局清晰删除业务信息。事实未知、过期或缺失应在视图中可识别。具体生成与阅读见 [项目架构可视化](architecture-visualization.md)。

拆分、移动或合并模块是架构变更：先确定身份与职责归属、契约和影响，再维护目录、入口、代码与测试，核对迁移前后事实、引用和证据。无需为升级布局迁移没有职责变化的代码。项目增长后，局部任务的读取范围主要随实际影响增长；全局检查可以遍历全部记录，但不要求每次设计都通读全部模块。

## 验收边界

真实验收至少覆盖：从零创建、深层定位、跨模块契约修改、模块移动/拆分、中断换执行者，以及故意破坏的路由/归属/依赖/证据。保留改造前基线，使用相同任务与未参与设计的新用例比较，检查功能展开、架构决策、专业子能力、代码质量、验证与长期接力是否退化。文档说明、字段完整和工具测试不能独立证明技能实际决策能力提升。
