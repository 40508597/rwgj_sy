# 模块拆分详细指南

## 核心问题：拆还是不拆？

拆分是架构设计中最关键的决策。拆得太粗，JSON 沦为形式；拆得太细，管理成本超过收益。

## 三层粒度判断

不要只问“要不要拆模块”。先判断当前对象属于哪一层：

| 粒度 | 解决什么问题 | 写入位置 | 停止标准 |
|------|--------------|----------|----------|
| 功能粒度 | 用户需求是否完整、可验收 | `功能树` | 叶子节点可验收、可落位、可测试 |
| 模块粒度 | 工程责任是否独立、边界是否清楚 | `模块树`、`模块拓扑`、`模块详情` | 叶子模块有职责、接口/文件/数据/测试落位 |
| 文件粒度 | 代码实现是否可维护 | `实现清单`、`完整细节` | 文件职责单一，开发者能直接编码 |

执行顺序固定为：先拆功能，再拆模块，再拆文件。不要用文件目录反推需求，也不要把一个用户功能直接落到一堆函数。

## 功能粒度决策

面对用户需求时，先判断功能树要不要继续展开。

### 应该继续拆功能

满足任一条件，继续拆成 L3/L4/L5：
- 一个功能名天然包含多个用户动作，如“菜单管理”包含新增、编辑、删除、排序、权限、空状态、异常反馈。
- 同一功能有多种角色视角，如管理员、普通用户、审计员看到的行为不同。
- 存在独立异常路径，如权限不足、数据为空、重复提交、网络失败。
- 验收标准无法一句话证明完成。
- 架构落位会跨多个模块、入口、数据表或测试。

### 应该停止拆功能

满足全部条件即可停止：
- 叶子节点有明确用户价值或系统行为。
- 已记录验收标准、异常路径、架构落位和验证责任。
- 再拆会进入按钮点击、函数语句或 CSS 属性级别。
- 一个不熟悉项目的人能判断这个叶子功能完成还是未完成。

## 模块粒度决策

功能叶子落位后，再判断是否需要父模块、子模块或叶子模块。

### 模块树拆分流程

1. 先找父模块：这个能力属于哪个领域、页面域、基础设施域或运行时域？
2. 再找子模块：父模块内部是否存在不同责任域、状态机、数据所有权或独立接口？
3. 最后找叶子模块：是否已经能落到文件、接口、数据和测试？
4. 把父子关系写入 `模块树`，把调用依赖写入 `模块拓扑.依赖图`。

### 应该拆成子模块

满足任一条件，拆成子模块：
- 有独立对外接口或会被其他模块直接依赖。
- 有独立数据读写责任或状态机。
- 有独立测试责任，失败时可以单独定位。
- 父模块文件数超过 5 个，或接口数超过 5 个，继续放一起会模糊。
- 子能力可被复用，如导入、导出、权限校验、搜索过滤、批量操作。

### 不应该拆成子模块

满足任一条件，保持在当前模块内部：
- 只是私有辅助函数、常量、样式片段或极小工具。
- 拆开后高度耦合，需要互相调用大量内部状态。
- 拆开会制造循环依赖。
- 预计不足 50 行且没有独立测试价值。
- 只是为了让 JSON 看起来更细，而没有真实工程边界。

## 文件粒度决策

模块树和模块详情确定后，再设计文件清单。

### 应该拆文件

满足任一条件，拆出文件：
- 文件混合了服务、仓储、模型、组件、样式、测试等不同责任。
- 单文件超过 300-500 行，且内部存在稳定子责任。
- 测试难以只针对一个责任编写。
- 多个模块重复同一实现片段，适合提取公共文件或公共模块。

### 不应该拆文件

满足任一条件，不拆：
- 拆开后只剩几行包装代码。
- 新文件没有稳定命名和稳定职责。
- 拆开后读代码必须频繁跳转，反而降低可维护性。
- 文件变化频率相同且总是一起修改。

## 模块拆分决策流程

当你面对一个模块时，按以下顺序判断：

### 第1步：职责检验

问自己："这个模块只做一件事吗？"

- "用户认证" → 只做一件事 ✓
- "用户认证和日志记录" → 两件事，应该拆 ✗
- "数据库连接管理" → 只做一件事 ✓

### 第2步：接口检验

问自己："这个模块有明确的对外的接口（导出）吗？"

- 有可以被其他模块调用的函数/类 → 有独立接口 ✓
- 所有函数只在模块内部使用 → 无独立接口，可能是工具模块

### 第3步：依赖检验

问自己："其他模块会依赖这个模块吗？"

- 会 → 应该独立成模块
- 不会 → 考虑合并到调用它的模块

### 第4步：可测试性检验

问自己："这个模块能独立运行测试吗？"

- 能（不需要启动整个应用）→ 适合独立
- 不能（必须依赖其他模块才能测试）→ 考虑合并

### 第5步：粒度检验

问自己："这个模块拆分后有足够的代码量吗？"

- 预计少于 50 行 → 可能不值得拆
- 预计超过 500 行 → 可能需要再拆

## 常见模式

### 模式1：三层架构（推荐用于 Web 后端）

```
数据层 (m1): 数据库连接、ORM 基类
  ↓
模型层 (m2): 数据模型定义（ORM + Schema）
  ↓
服务层 (m3): 业务逻辑
  ↓
接口层 (m4): API 路由
```

每层一个模块，依赖单向流动。这是最安全的拆分方式。

### 模式2：领域驱动（推荐用于复杂业务）

```
共享基础设施 (m1): 数据库、日志、配置
  ↓
用户领域 (m2): 用户模型 + 用户服务
订单领域 (m3): 订单模型 + 订单服务
  ↓
用户 API (m4): 用户路由
订单 API (m5): 订单路由
```

每个业务领域一个模块，公共部分抽到基础设施。

### 模式3：功能模块（推荐用于 CLI 工具）

```
配置管理 (m1): 读取/解析配置
  ↓
命令A (m2): 功能A实现
命令B (m3): 功能B实现
  ↓
主入口 (m4): CLI 参数解析和分发
```

## 反面模式（应该避免）

### 反面1：过度拆分

```
❌ 不好：
m1: 仅一个数据库连接函数
m2: 仅一个 User 模型类
m3: 仅一个 create_user 函数
m4: 仅一个 GET /users 路由

✅ 好：
m1: 数据库连接 + ORM 基类（2个文件）
m2: 用户模型 + 用户服务（3个文件）
m3: 用户 API 路由（2个文件）
```

### 反面2：循环依赖

```
❌ 不好：
m1 依赖 m2，m2 依赖 m1 → 循环！

✅ 好：
提取公共部分到 m0，m1 和 m2 都依赖 m0
或：合并 m1 和 m2 为一个模块
```

### 反面3：按文件类型拆分

```
❌ 不好：
m1: 所有 models
m2: 所有 services
m3: 所有 routes

✅ 好：
m1: 用户（model + service + route）
m2: 订单（model + service + route）
```

按文件类型拆（所有 model 在一起）看似整齐，但修改一个功能要跨多个模块，违背了"高内聚低耦合"原则。

## 拆分自检清单

在最终确定架构前，逐项检查：

- [ ] 每个模块是否只有一个明确的职责？
- [ ] 每个模块是否有清晰的对外接口（导出）？
- [ ] 依赖关系是否单向无环（DAG）？
- [ ] 每个模块是否能独立测试？
- [ ] 每个模块的文件数是否在 1-5 个？
- [ ] 有没有模块预计少于 50 行代码？
- [ ] 修改一个业务功能时，是否只影响少数模块？
