# 模块拆分详细指南

## 核心问题：拆还是不拆？

拆分是架构设计中最关键的决策。拆得太粗，JSON 沦为形式；拆得太细，管理成本超过收益。

## 三层粒度判断

不要只问“要不要拆模块”。先判断当前对象属于哪一层：

| 粒度 | 解决什么问题 | 写入位置 | 停止标准 |
|------|--------------|----------|----------|
| 功能粒度 | 用户需求是否完整、可验收 | `功能树` | 实施叶子可验收、可落位、可测试；候选保留取舍依据 |
| 模块粒度 | 工程责任是否独立、边界是否清楚 | `模块树`、`模块拓扑`、`模块详情` | 叶子模块有职责、接口/文件/数据/测试落位 |
| 文件粒度 | 代码实现是否可维护 | `实现清单`、`完整细节` | 文件职责单一，开发者能直接编码 |

新设计先理解功能，再确定模块和文件；已有项目纳管先记录实际代码边界，再核对需求与治理建议，不把现状当理想设计。不要仅凭文件目录杜撰需求，也不要把一个用户功能直接落到一堆函数。

## 功能粒度决策

面对用户需求时，先判断功能树要不要继续展开。

### 应该继续拆功能

满足任一条件，继续向下展开（层级名称仅辅助理解，不限制深度）：
- 一个功能名天然包含多个用户动作，如“菜单管理”包含新增、编辑、删除、排序、权限、空状态、异常反馈。
- 同一功能有多种角色视角，如管理员、普通用户、审计员看到的行为不同。
- 存在独立异常路径，如权限不足、数据为空、重复提交、网络失败。
- 验收标准无法一句话证明完成。
- 架构落位会跨多个模块、入口、数据表或测试。

### 应该停止拆功能

本轮实施叶子满足全部条件即可停止；待确认、延期、排除或不适用候选按 [候选状态与本轮实施范围](function-clusters.md#候选状态与本轮实施范围) 保留依据与继续条件，不强求实施细节，也不删除全景：
- 叶子节点有明确用户价值或系统行为。
- 已记录验收标准、异常路径、架构落位和验证责任。
- 再拆会进入按钮点击、函数语句或 CSS 属性级别。
- 一个不熟悉项目的人能判断这个叶子功能完成还是未完成。

## 模块粒度决策

功能叶子落位后，再判断是否需要父模块、子模块或叶子模块。

### 模块树拆分流程

1. 先找父模块：这个能力属于哪个领域、页面域、基础设施域或运行时域？
2. 再找子模块：父模块内部是否存在不同责任域、状态机、数据所有权或独立接口？
3. 最后找叶子模块：是否已经能落到文件、接口、数据和测试？
4. 新项目以模块目录和 `模块路由` 记录直接父子入口；集中布局使用 `模块树`。调用依赖独立写入 `模块拓扑.依赖图`，详见 [递归模块](recursive-modules.md)。

### 应该拆成子模块

满足任一条件，拆成子模块：
- 有独立对外接口或会被其他模块直接依赖。
- 有独立数据读写责任或状态机。
- 有独立测试责任，失败时可以单独定位。
- 父模块内部出现稳定的独立责任，继续混放会增加理解、协作或验证成本。
- 子能力可被复用，如导入、导出、权限校验、搜索过滤、批量操作。

### 不应该拆成子模块

满足任一条件，保持在当前模块内部：
- 只是私有辅助函数、常量、样式片段或极小工具。
- 拆开后高度耦合，需要互相调用大量内部状态。
- 拆开会制造循环依赖。
- 缺少独立语义、状态或验证边界，拆开只增加跳转。
- 只是为了让 JSON 看起来更细，而没有真实工程边界。

## 文件粒度决策

模块树和模块详情确定后，再设计文件清单。

### 应该拆文件

满足任一条件，拆出文件：
- 文件混合了服务、仓储、模型、组件、样式、测试等不同责任。
- 单文件超过 300-500 行，且内部存在稳定子责任。
- 测试难以只针对一个责任编写。
- 多个模块重复同一实现片段，适合提取公共文件或公共模块。

### 不应该拆文件

满足任一条件，不拆：
- 拆开后只剩几行包装代码。
- 新文件没有稳定命名和稳定职责。
- 拆开后读代码必须频繁跳转，反而降低可维护性。
- 文件变化频率相同且总是一起修改。

## 模块拆分决策流程

当你面对一个模块时，按以下顺序判断：

### 第1步：职责检验

问自己："这个模块只做一件事吗？"

- "用户认证" → 只做一件事 ✓
- "用户认证中记录认证事件" → 可是认证责任的一部分；通用日志管道若有独立契约与生命周期，再考虑拆出
- "数据库连接管理" → 只做一件事 ✓

### 第2步：接口检验

问自己："这个模块有明确的对外的接口（导出）吗？"

- 有可以被其他模块调用的函数/类 → 有独立接口 ✓
- 所有函数只在模块内部使用 → 无独立接口，可能是工具模块

### 第3步：依赖检验

问自己："其他模块会依赖这个模块吗？"

- 会 → 检查被依赖的是稳定对外契约还是私有细节；前者支持独立，后者应先修正边界
- 不会 → 按数据/状态归属和测试收益判断，不因暂无消费者就强制合并

### 第4步：可测试性检验

问自己："这个模块能独立运行测试吗？"

- 能（不需要启动整个应用）→ 适合独立
- 不能 → 先区分独立行为测试和必要集成测试；只有无法形成合理边界且合并有收益时才考虑合并

### 第5步：粒度检验

问自己："拆分后，职责、契约和验证收益是否大于导航与协作成本？"

- 小模块若有稳定职责、公共契约或独立验证价值，可以保留。
- 大模块若存在稳定子责任且拆分能降低耦合与验证成本，可以继续拆；行数只是调查线索，不是门槛。

## 常见模式

### 模式1：横向分层（候选，适用于有明确技术边界的工程）

```
接口层: API 路由
  ↓ 依赖
服务层: 业务逻辑
  ↓ 依赖
模型/数据访问层: 数据契约与存储访问
  ↓ 依赖
数据库适配: 连接与工程实际需要的能力
```

这些首先是内部代码层，不自动对应受管模块或独立架构文件。层具有稳定技术契约、独立维护/替换或验证需求时，可以成为受管模块；否则可留在同一业务模块内部。优点是技术边界明确；代价是业务变更可能跨层协调，应核对契约与验证成本。箭头仅表示调用依赖，不表示层级高低或执行顺序。

### 模式2：领域组织（候选，适用于业务与数据边界较稳定的工程）

```
用户 API → 用户领域（数据契约 + 业务行为）
订单 API → 订单领域（数据契约 + 业务行为）
用户领域 / 订单领域 → 实际需要的共享技术适配
箭头表示依赖；API 可以是领域内部代码层，不预设独立模块
```

业务变化集中、状态与数据责任可明确归属时，可按领域组织受管模块，内部仍可分层；领域的 API 是否独立模块按契约与维护收益决定。优点是同类业务变更局部化；代价是跨领域事务、共同契约与适配重复需要协调。只有确实共享且职责稳定的部分才抽出，不预设独立基础设施模块。

### 模式3：功能组织（候选，常见于 CLI 等任务入口明确的工程）

```
主入口（CLI 参数解析和分发）→ 命令A / 命令B
命令A / 命令B → 实际需要的配置读取或共享行为
箭头表示依赖；每项是否独立模块取决于职责与验证收益
```

命令具有独立行为与测试边界时可按功能组织；小工具可在一个模块内保留入口和命令实现，不为这张示意图强拆配置或分发模块。

## 边界失配模式（按实际代价判断）

### 反面1：过度拆分

```
❌ 不好：
m1: 仅一个数据库连接函数
m2: 仅一个 User 模型类
m3: 仅一个 create_user 函数
m4: 仅一个 GET /users 路由

✅ 好：
m1: 数据库连接 + ORM 基类（2个文件）
m2: 用户模型 + 用户服务（3个文件）
m3: 用户 API 路由（2个文件）
```

### 反面2：循环依赖

```
❌ 不好：
m1 依赖 m2，m2 依赖 m1 → 循环！

✅ 好：
提取公共部分到 m0，m1 和 m2 都依赖 m0
或：合并 m1 和 m2 为一个模块
```

### 反面3：仅按文件类型划受管模块，却没有稳定技术契约

```
❌ 不好：
m1: 所有 models
m2: 所有 services
m3: 所有 routes

✅ 好：
m1: 用户（model + service + route）
m2: 订单（model + service + route）
```

问题不是目录名或横向分层本身，而是仅靠文件类型制造模块边界：若业务变化频繁跨层、私有细节互相暴露且没有独立技术/验证收益，应考虑领域聚合。若各层有稳定契约及独立维护价值，模式1仍是合理候选。比较真实变更跨度、状态归属、耦合与验证成本后选择；不因采用某种模式就迁移整个已有项目。

## 拆分自检清单

在最终确定架构前，逐项检查：

- [ ] 每个模块是否只有一个明确的职责？
- [ ] 每个模块是否有清晰的对外接口（导出）？
- [ ] 依赖关系是否单向无环（DAG）？
- [ ] 每个模块是否能独立测试？
- [ ] 模块边界是否由职责、状态/数据归属、对外契约与验证边界决定，而非固定文件数？
- [ ] 较小或较大的实现是否仍有独立职责与合理拆分收益？行数只作为审查线索。
- [ ] 修改一个业务功能时，是否只影响少数模块？
