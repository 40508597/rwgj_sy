# 五个命令

### `/分析架构` — 从代码逆向生成架构

**触发**：已有项目代码，想纳入架构管理。

**迁入原则**：先现状画像，再治理建议。不要把代码真实存在的现状和理想补全混在同一层结论里。

**流程**：
1. 扫描项目目录结构，识别技术栈和框架
2. 分析模块边界（目录结构 + import关系 + 类/函数职责聚类）
3. 提取每个模块的导出接口（函数签名、类方法）
4. 构建模块依赖图（从 import 语句推导）
5. 生成**现状画像**：只记录当前代码真实存在的模块、入口、接口、数据、文件、测试
6. 对照功能簇和完整性检查清单，生成**治理建议**：缺失的商业标配、功能簇缺口、架构风险
7. 生成 `architecture/` 架构文件夹，并明确哪些是已实现，哪些是建议/计划中
8. 汇报：架构概况 + 现状画像 + 治理建议 + 完整性检查结果

**关键**：主动指出缺失的基础设施模块（没有日志？没有迁移？没有健康检查？），这些是已有项目最常见的缺口。

### `/创建架构` — 从零搭建项目架构

**触发**：新项目从零开始。

**流程**：

```
全景分析层：
  1. 理解需求 → 功能簇展开（标准展开列出核心+衍生子功能→用户确认范围）
  2. 功能树建模（功能簇 → L0-L5 节点 → 叶子节点验收/异常/落位/验证责任）
  3. 专业能力索引匹配（判断是否需要 UI/测试/安全/性能/客户端/可执行交付/部署/文档等已有技能辅助）
  4. 确定项目类型 → 五大维度启用哪些
  5. 最大主动性设计：主动补全缺失关注点
  6. 推荐技术栈

拆块与骨架层：
  7. 拆块清单（名称、优先级、依赖关系）
  8. 基础设施模块详细定义（配置/日志/错误/迁移/健康检查）
  9. 运行时+入口架构定义
  10. 生成骨架 `architecture/` 架构文件夹（包含功能树、专业能力索引、模块拓扑、模块树、模块详情和基础设施，不包含未设计完成的业务实现细节）

逐块深度设计层：
  11. 按功能树和依赖顺序自动逐块深度设计 → 更新架构切片 → 编码 → 测试
  12. 实现中发现功能族缺口时，先暂停编码，局部展开当前功能节点，更新架构切片后再继续
  13. 每块完成后提取接口签名摘要，传给下一块

集成验证层：
  14. 检查功能树落位、专业能力回写、接口一致性和验证证据 → 汇报总结
```

**禁止**：在骨架层预定义业务模块。骨架架构文件夹只有基础设施。业务模块只在逐块深度设计层加入。

### `/修改架构` — 修改已有内容

**触发**：修改已存在的模块/文件/接口/表/组件/路由等任何已在架构文件夹中登记的内容。

**与 /追加架构 的边界**：
- 改已有模块的任何东西（文件/接口/状态）→ `/修改架构`
- 新增一个架构文件夹中不存在的模块 → `/追加架构`
- 给已有模块新增文件或导出接口 → `/修改架构`（不是追加，是修改已有模块）

**流程**：
1. 读取根指针、总索引和相关切片，定位目标模块
2. **影响范围分析**（修改前必做）：
   - 从依赖图找出所有依赖目标模块的下游模块
   - 判断变更级别：接口级（破坏性）还是实现级（非破坏性）
   - 接口级变更 → 列出所有受影响的下游接口调用点
3. 更新架构切片 + 追加变更记录
4. **级联处理**：
   - 接口签名变化 → 重置所有下游模块状态为"计划中"，按依赖顺序重新验证
   - 内部实现变化 → 只改当前模块状态，下游模块不受影响
   - 删除导出 → 检查下游是否存在悬空依赖，如有则必须同步修改下游
5. 按更新后的架构文件夹修改代码 + 运行受影响模块的测试
6. 编码或测试中发现状态、异常、权限、数据、接口、反馈或验证责任缺口时，进入实现期功能族循环展开：暂停编码 → 更新架构切片 → 重新确认影响范围 → 继续实现

**安全修改模式**：

| 变更类型 | 影响范围 | 处理方式 |
|---------|---------|---------|
| 改函数内部实现 | 仅当前模块 | 改代码→跑测试→完成 |
| 新增导出接口 | 仅当前模块 | 更新架构切片→加代码→加测试 |
| 改接口参数（新增可选参数） | 当前模块 | 向后兼容，下游不受影响 |
| 改接口参数（改类型/删参数） | 当前+所有下游 | 先更新所有下游的调用代码，再改当前模块 |
| 改数据库表结构 | 当前+所有操作该表的模块 | 先写迁移脚本，再依次更新各模块 |
| 拆分模块 | 新增模块+原模块+下游 | 先创建新模块→迁移接口→更新下游引用→删除旧代码 |
| 合并模块 | 合并后的模块+下游 | 先创建合并模块→迁移所有接口→更新下游引用→删除旧模块 |

### `/追加架构` — 新增不存在的模块

**触发**：新增架构文件夹中不存在的模块/功能。

**流程**：
1. 读取根指针、总索引和相关切片
2. 功能簇展开（用户说的功能名 → 展开核心+衍生子功能 → 用户确认范围）
3. 功能树建模（把新增功能挂到既有功能域/功能组；没有合适父节点时新增功能域）
4. 专业能力索引匹配（如页面/UI、E2E、安全、性能、客户端、可执行交付、部署、文档等需要专业能力）
5. 补模块树（确认新增能力挂到哪个父模块；必要时拆出子模块和叶子模块）
6. 补模块详情（职责、非职责、内部结构、数据读写、错误边界、配置、安全、测试责任）
7. 确认后自动拆块 → 逐块深度设计 → 自动推进
8. 全部完成后汇报

**单块模式**：如果新增内容不超过一个块的规模，直接深度设计+编码+测试。

### `/校验架构` — 校验架构文件夹与代码一致性

**触发**：用户要求检查项目是否漂移，或在完成创建/分析/追加/修改后收尾验证。

**流程**：
1. 读取 `architecture/` 架构文件夹中的项目骨架、契约、清单和细节层
2. 对照代码目录、入口、路由、接口、数据结构、测试文件
3. 检查代码中是否存在架构文件夹未定义的模块/文件/接口
4. 检查架构文件夹中定义但代码缺失、测试缺失或状态过期的节点
5. 输出一致性报告：通过项、偏差项、风险等级、建议修复顺序
6. 如用户要求修复，先更新架构切片，再按 `/修改架构` 或 `/追加架构` 执行

**输出必须包含**：
- 总体结论：一致 / 轻微漂移 / 严重漂移
- 偏差清单：架构有代码无、代码有架构无、契约不一致、测试缺失
- 影响范围：受影响模块、接口、页面、数据、测试
- 修复建议：先改架构切片、先改代码、或需要用户确认的分歧点

**偏差分类**：
- 架构漏登记：代码真实存在且合理，先补架构切片，再校验
- 代码越界：代码超出架构定义且无合理依据，回收代码或先登记后评估
- 架构设计错误：先修改架构切片，再按新架构修改代码
- 真实代码代表现状：走 `/分析架构` 同步现状，再输出治理建议

### 漂移修复模式

当发现架构文件夹与代码不一致时，不要直接“以代码为准”或“以架构为准”。先分类，再修复。

```
发现漂移
  ↓
列出差异：代码有架构无 / 架构有代码无 / 契约不一致 / 测试缺失 / 验证证据缺失
  ↓
判断来源：
  A. 合理实现但漏登记 → 先补架构切片，再校验
  B. 临时实现或越界实现 → 回收代码，或先登记为待确认再评估
  C. 架构设计过期 → 先更新架构切片，再按新架构改代码
  D. 需求不清导致分歧 → 写入未决问题，暂停破坏性修改
  ↓
补齐：功能树、模块树、模块详情、接口契约、实现清单、测试责任、验证证据
  ↓
运行受影响测试和 21 项校验
  ↓
写入变更记录：漂移类型、修复方式、影响范围、剩余风险
```

**漂移修复优先级**：
1. 先修契约漂移：接口签名、路由、数据结构不一致会影响下游。
2. 再修落位漂移：文件、模块树、实现清单缺登记会影响可追踪。
3. 再修测试漂移：功能已变但测试责任未更新。
4. 最后修文档性漂移：说明、状态、恢复点过期。

**禁止**：
- 不得因为“代码已经能跑”就跳过架构补登记。
- 不得把明显越界代码直接登记成正式设计，除非先评估其功能树、模块树和依赖影响。
- 不得只改架构切片不处理代码中已经存在的冲突实现。

## 状态流转

```
模块状态：计划中 → 编写中 → 待测试 → 测试中 → 已完成
              │         │           │
              └── 已废弃 ←── 修复中 ←─┘

文件状态：计划中 → 编写中 → 已完成 → 待审查
              │         │
              └── 已废弃 ←── 修复中
```

**转换规则**：
- 模块依赖的所有模块必须"已完成"，该模块才能"编写中"
- 模块下所有文件"已完成"后，模块自动变为"待测试"
- 测试失败 → 相关模块和文件变为"修复中"

## 拆分原则

**应该拆**（满足任一）：有独立对外接口、被其他模块依赖、可独立编译测试、职责明显不同、可作为父模块下稳定子模块。
**不应该拆**（满足任一）：仅内部辅助函数、会循环依赖、文件预计<50行、拆分后高度耦合。
**粒度**：一个模块 1~5 个文件。超过 5 个考虑再拆，但必须有职责上的理由。

**三层粒度**：
- 功能粒度：拆到可验收、可落位、可测试。
- 模块粒度：拆到有父子归属、职责边界、接口/文件/数据/测试落位。
- 文件粒度：拆到文件职责单一，继续拆会变成函数级细节。

## 工作流程

### 执行前门禁

在创建、分析、追加、修改之前，先回答并记录：

1. 当前目录或项目根目录是否存在根指针 `architecture.json` 或 `architecture/` 架构文件夹？
   - 存在：默认这是受管项目。任何代码、UI、接口、数据、测试、文件或行为修改都必须先转读 `architecture/index.json` 和相关切片，先更新架构文件夹，再改代码。
   - 不存在：判断是否需要 `/创建架构` 或 `/分析架构`；一次性脚本、小 demo、临时小修可以不调用本技能。
2. 用户是否明确要求跳过架构文件夹？
   - 是：说明会产生代码漂移风险；如仍执行，最终必须记录“本次未更新 architecture/ 架构文件夹”。
   - 否：不得绕过架构文件夹直接改代码。
3. 这是创建、分析、追加、修改还是校验？不要把新增模块误判为修改，也不要把已有模块加文件误判为追加。
4. 根指针和 `architecture/` 架构文件夹是否可信？明显过期先走 `/校验架构`。
5. 本次变更的最小闭环是什么？明确要覆盖的模块、接口、文件、数据、交互和测试。

第一段输出必须使用 `references/execution-templates.md` 中的“任务前置输出模板”。任务完成前必须对照“完成定义”。测试失败、实现卡住或等待用户时，使用“失败恢复模板”更新上下文恢复点。

### 实现期功能族循环展开

设计好架构并开始编码后，架构不是冻结的。实现过程中如果发现当前功能节点的自然边界还没有展开完整，应进行局部循环，而不是把发现的能力直接写进代码。

```text
当前模块开始实现
  ↓
发现缺口：状态 / 异常 / 权限 / 数据 / 接口 / 交互反馈 / 测试责任
  ↓
停止当前代码修改
  ↓
回到 `architecture/index.json` 或相关切片展开当前功能族或子功能节点
  ↓
分类：必须补 / 建议补 / 待确认 / 明确排除
  ↓
更新功能树、模块详情、接口契约、实现清单、测试责任
  ↓
继续实现并验证
  ↓
叶子节点闭合后退出循环
```

循环边界：
- 只展开当前模块、当前功能节点和直接依赖契约，不借机全局重构。
- 必须补内容可以进入本轮；建议补和待确认内容不得悄悄实现。
- 用户明确不要的内容优先排除，并写入恢复点或非目标。
- 循环退出后必须有验证证据或明确阻塞原因。

### 受管项目默认路由

当项目中存在根指针 `architecture.json` 或 `architecture/` 架构文件夹时，用户即使没有输入命令，也按以下规则自动路由。用户只说“使用任务架构”“按这个技能”“按架构来”“按照 architecture.json”时，也必须先自动判断命令类型，不得等待用户补命令或直接改代码。

| 用户说法 | 默认命令 | 说明 |
|------|------|------|
| “使用任务架构/按这个技能/按架构来” | 自动判定 | 根据后续任务内容选择分析、创建、修改、追加或校验 |
| “改一下页面/删掉标题/调整按钮/优化 UI” | `/修改架构` | UI 属于页面拓扑、完整细节和验证证据的一部分 |
| “修一个 bug/报错/异常” | `/修改架构` | 先补 Bug 场景、异常路径和测试责任，再修代码 |
| “加一个功能/新增页面/新增接口/新增后台任务/新增CLI命令/新增窗口/新增托盘/新增安装包/新增Docker镜像/新增SDK包/新增模块” | `/追加架构` | 架构文件夹中不存在的新能力先进入功能树、运行形态、入口、交付物、系统集成和模块拓扑 |
| “改字段/表结构/接口参数” | `/修改架构` | 先更新数据拓扑或接口契约，再改迁移/代码 |
| “重构/优化性能/调整目录” | `/修改架构` | 先更新影响范围、模块状态和变更记录 |
| “检查是否一致/为什么不对” | `/校验架构` | 先分类架构漏登记、代码越界或架构设计错误 |

禁止把“很小的修改”当作绕过架构文件夹的理由。受管项目的小修改也会导致长期漂移。

### 无命令自动判定规则

用户没有写 `/分析架构`、`/创建架构`、`/修改架构`、`/追加架构`、`/校验架构` 时，按以下顺序判定：

1. 要求检查、评估一致性、找漂移、解释为什么不对 → `/校验架构`
2. 已有代码但没有可信根指针或 `architecture/` 架构文件夹，要求纳入管理 → `/分析架构`
3. 没有代码或明确从零开始 → `/创建架构`
4. 要做架构文件夹中不存在的新功能/新模块/新页面/新接口 → `/追加架构`
5. 要改已有功能、修 Bug、删 UI、改字段、调样式、优化性能、重构已有模块 → `/修改架构`

第一段汇报必须写明“自动判定命令：...”。若无法判定，先问一个澄清问题，不得先改代码。

### 从架构文件夹到代码

```
architecture/ 架构文件夹就绪
    ↓
按优先级顺序，每个模块：
  1. 读第1层确认依赖模块是否全部"已完成"（是则继续，否则等待）
  2. 读第1层的模块树确认父模块、子模块、叶子模块和落位
  3. 读第1层的模块详情确认职责、非职责、内部结构、数据责任和错误边界
  4. 读第2层获取当前模块的接口契约（导出什么+依赖谁）
  5. 读第3层获取文件清单+数据表DD→创建目录和文件骨架
  6. 读第4层获取当前模块的完整细节→按接口签名填充实现→按测试用例生成测试
  7. 运行测试 → 通过则标记"已完成" → 进入下一模块
```

**四层读取逐模块递进**：写 m6 时只读 m6 的第4层 + 它依赖模块（m4, m2）的第2层。不读无关模块的任何层。

### 完整开发流程

```
/创建架构 或 /分析架构 → architecture/ 架构文件夹就绪
    ↓
逐块设计 + 编码 + 测试 → 自动推进直到全部"已完成"
    ↓
集成验证 → 最终产物
```

### 中断恢复

动手前自检：说不出「当前任务/当前阶段/下一步」即视同已被压缩，先按 `references/context-recovery.md` 读恢复点再动作。

读取 `architecture/tasks/state.json` 的 `上下文恢复点` 和状态字段即可知道：哪些已完成、哪些进行中、下一个该做什么。

恢复顺序：
1. 读取 `上下文恢复点`：当前任务、当前阶段、继续位置、下一步、未验证项、用户明确约束。
2. 读取第1层项目骨架和当前模块的第2-4层。
3. 检查 `已触碰文件` 和实际文件差异，确认是否有未记录代码漂移。
4. 从 `下一步` 的第一项继续，不要从头重新设计。
5. 完成后更新 `上下文恢复点`、`验证证据` 和 `变更记录`。

如果项目启用了 `架构切片`，恢复时先读根 `architecture.json`；若它指向 `architecture/index.json`，必须转读架构文件夹总索引，再只读取 `进行中模块` 或 `下一步` 指向的切片。切片细节见 `references/json-sharding.md`。

### 调试与排错

**`architecture/` 架构文件夹也是排错地图。当出现 Bug 时，利用架构切片中的以下信息快速定位：**

**定位流程**：
```
Bug 报告 → 确定出问题的模块编号
    │
    ├── 查架构切片的依赖字段 → 是上游传错数据，还是本模块逻辑错误？
    │   如果上游接口返回的数据不对 → 追溯到上游模块
    │
    ├── 查架构切片的接口.导出 → 实际调用参数是否符合接口签名？
    │   参数类型不匹配 → 调用方的问题
    │   参数正确但结果错误 → 本模块实现问题
    │
    ├── 查架构切片的接口.可能异常 → 这个异常是否被正确处理？
    │   未列出的异常 → 架构定义不完整，需更新
    │   已列出但未捕获 → 代码实现遗漏
    │
    └── 查架构切片的测试用例 → 这个 Bug 场景是否有覆盖？
        没有 → 先补测试用例到架构切片，再修代码
        有但测试未发现 → 测试实现有误，修正测试
```

**常见排错模式**：

| 症状 | 架构诊断 | 修复方式 |
|------|---------|---------|
| 模块A调用模块B报错 | 检查B的接口签名和可能异常 | 如A的参数不符合签名→修A；如B少列了异常→更新B的架构切片 |
| 数据表字段缺失 | 检查数据架构中的表定义 | 表定义不完整→`/修改架构`补字段+写迁移 |
| 组件状态异常 | 检查组件的状态展示五态定义 | 某态未定义→补定义；实现不符合定义→修代码 |
| 循环依赖报错 | 检查依赖图 | `/修改架构`重构去除循环 |
| 测试通过但线上异常 | 检查测试用例是否覆盖该场景 | 补测试用例到架构切片→补测试代码→复现→修复 |

**修复后必须做的事**：
1. 更新架构变更记录（原因写明 Bug 根因）
2. 补充测试用例到架构切片（覆盖本次 Bug 场景）
3. 检查是否有同类问题存在于其他模块（同类接口、同类组件）

### 项目优化

**优化项目 = 优化 `architecture/` 架构文件夹，然后重新生成代码。** 不存在"绕过架构文件夹直接优化代码"的路径。

**优化发现**：定期检查 `architecture/index.json` 和相关切片中的以下信号自动发现优化点：

```
信号1: 模块文件数 > 5 → 考虑拆分
信号2: 模块文件数 = 1 且 < 50行 → 考虑与相关模块合并
信号3: 依赖链深度 > 4 → 中间层可能过度抽象
信号4: 同一模块被 5+ 个模块依赖 → 考虑是否过于中心化
信号5: 测试用例仅覆盖 happy path → 补充边界和异常测试
信号6: 变更记录中同一模块频繁修改 → 接口设计可能不稳定
信号7: 多个模块有相同的导出签名 → 提取公共接口/基类
信号8: 组件树的属性很多但默认值为空 → 组件可能过度设计
```

**优化决策矩阵**：

| 优化目标 | 识别方式 | 操作 |
|---------|---------|------|
| 性能优化（接口不变） | 分析/监控发现瓶颈 | 更新目标模块变更记录 → 改实现 → 跑测试 |
| 重构拆分 | 模块文件 > 5 或职责混杂 | `/修改架构`拆成2个模块 → 定义新接口和依赖 → 逐模块重写 |
| 重构合并 | 小模块且高度耦合 | `/修改架构`合并 → 更新接口列表 → 合并代码 |
| 消除循环依赖 | 依赖图分析发现环 | `/修改架构`重构依赖关系 → 可能需要提取公共接口 |
| 补充测试覆盖 | 测试用例缺少边界/异常 | 更新架构切片测试用例 → 补测试代码 |
| 升级框架/库 | `项目` 中的版本号 | `/修改架构`更新 `项目` + 受影响模块接口 → 逐模块适配 |
| 提取公共代码 | 多模块重复的导出签名 | `/追加架构`新增公共模块 → `/修改架构`让各模块依赖公共模块 |

**优化原则**：
- 先改架构文件夹再改代码——优化的第一步永远是更新 `architecture/index.json` 或相关切片
- 一次优化只做一件事——不要同时拆分+合并+升级
- 每次优化后跑全部受影响模块的测试——不只是当前模块
- 优化完成后在变更记录中注明"为什么优化"（性能数据？可维护性？）

### 架构切片

受管项目默认启用 `architecture/` 架构文件夹。切片不是改变真相源，也不是散放多个 JSON，而是把真相源拆成“架构文件夹总索引 + 局部事实文件”。

启用前提：
- 项目已进入任务架构管理；根 `architecture.json` 只作为指针。
- `architecture/index.json` 总索引仍能回答项目身份、功能域、模块树、模块拓扑、切片位置和上下文恢复点。
- 每个切片只承载一个功能域、模块、页面、数据对象或当前任务。

执行规则：
1. 先创建 `architecture/` 文件夹和 `architecture/index.json`，再创建或移动切片文件。
2. 跨切片依赖必须回写总索引的 `模块拓扑.依赖图`。
3. 修改切片后，必须更新切片变更记录和总索引变更摘要。
4. 总索引与切片冲突时，先走 `/校验架构` 分类，不得直接覆盖。

完整协议见 `references/json-sharding.md`。
