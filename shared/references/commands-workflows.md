# 五个命令

新项目默认采用 [递归模块架构](recursive-modules.md)：根 `architecture.json` 是项目总架构，每个受管模块目录有本模块架构。既有集中切片跟随根指向与切片登记继续读取。下文“项目架构”包括这两种已明确登记的布局；不要把集中目录规定套到递归模块，也不为形式移动已有源码。

### `/分析架构` — 从代码逆向生成架构

**触发**：已有项目代码，想纳入架构管理。

**迁入原则**：先现状画像，再治理建议。不要把代码真实存在的现状和理想补全混在同一层结论里。

**流程**：
1. 扫描项目目录结构，识别技术栈和框架
2. 分析模块边界（实际目录、入口、调用/数据关系、实现职责和测试归属）
3. 提取模块对外契约（可取得的函数/过程、消息、命令、数据或其他调用形式）
4. 构建有证据的依赖图；语言解析器可补充观察，不以 import/AST 支持为前提，动态或不可采集的关系标明未知
5. 生成**现状画像**：只记录当前代码真实存在的模块、入口、接口、数据、文件、测试
6. 对照功能簇和完整性检查清单，生成**治理建议**：缺失的商业标配、功能簇缺口、架构风险
7. 按现有工程目录登记项目与模块架构，明确已实现、待实施与历史事实；不为新布局搬动无关代码
8. 汇报：架构概况 + 现状画像 + 治理建议 + 完整性检查结果

**关键**：核对本项目适用的工程责任及其实际承担位置，如错误处理、配置、日志、持久数据迁移或服务健康检查。责任缺失才列为治理缺口；已有模块能合理承担时，不要求另建基础设施模块。无持久模式变化的库不强制迁移，非常驻服务不强制健康端点；不适用项注明简短依据。适用性不削减功能全景，治理建议与本轮实施取舍分别记录。

递归布局可用 `module_architecture.py add --adopt-existing` 显式接入已有模块目录，仅新增缺失架构与父路由，不移动或改写源码；已有本模块架构时不能覆盖。新登记仍需按现状补齐事实、标明计划与未知项。

### `/创建架构` — 从零搭建项目架构

**触发**：新项目从零开始。

**流程**：

```
全景分析层：
  1. 理解需求 → 功能簇标准展开（核心+天然绑定+适用商业标配+强相关衍生与关联功能全景→用户取舍与已有授权）
  2. 功能树建模（功能簇 → 按需要递进的功能节点 → 叶子节点验收/异常/落位/验证责任；不以固定层数限制展开）
  3. 专业能力索引匹配（判断是否需要 UI/测试/安全/性能/客户端/可执行交付/部署/文档等已有技能辅助）
  4. 确定项目类型 → 五大维度启用哪些
  5. 最大主动性设计：主动补全缺失关注点
  6. 推荐技术栈

拆块与骨架层：
  7. 比较必要方案，确定全局目标约束、模块职责、共同契约、数据归属与拆块清单（名称、优先级、依赖关系）
  8. 核对适用工程责任及承担模块（配置/日志/错误/迁移/健康检查等）；有独立职责与验证收益才拆模块，不适用项说明依据
  9. 定义实际运行形态与入口，不强制引入服务、数据库或部署组件
  10. 生成根总架构与真实模块目录、各模块 architecture.json（已确认职责、契约与路由骨架；未完成细节标为待设计，不伪装为实现完成）

逐块深度设计层：
  11. 按功能树和依赖顺序自动逐块深度设计 → 更新拥有本次事实的模块架构 → 编码 → 测试
  12. 实现中发现功能族缺口时，先暂停编码，局部展开当前功能节点，更新架构切片后再继续
  13. 每块完成后提取接口签名摘要，传给下一块

集成验证层：
  14. 检查功能树落位、专业能力回写、接口一致性和验证证据 → 汇报总结
```

骨架可以建立经过职责设计的业务模块入口，不能提前杜撰未设计完成的业务细节、契约或验证结论。按需读取与分批实现不限制功能全景，用户已有授权范围内可连续推进。

### `/修改架构` — 修改已有内容

**触发**：修改已存在的模块/文件/接口/表/组件/路由等任何已在项目架构中登记的内容。

**与 /追加架构 的边界**：
- 改已有模块的任何东西（文件/接口/状态）→ `/修改架构`
- 新增一个项目架构中不存在的模块 → `/追加架构`
- 给已有模块新增文件或导出接口 → `/修改架构`（不是追加，是修改已有模块）

**流程**：
1. 读取根总架构，沿职责路由逐层定位相关模块；集中布局跟随指针与切片登记。取得当前模块契约、源码、测试和必要的依赖方信息，跨模块任务保留多条定位路径
2. **影响范围分析**（修改前必做）：
   - 从依赖图找出所有依赖目标模块的下游模块
   - 判断职责、接口、行为、数据、错误、性能或内部实现的变化；签名不变不自动等于消费者无影响
   - 契约级变更 → 列出受影响消费者、调用点和验证责任；工具结果基于已记录关系，补查未采集关系
3. 更新事实所属根/模块架构 + 追加变更依据；上层仅在入口、职责摘要或共同约束变化时同步
4. **级联处理**：
   - 契约变化 → 标记受影响验证待复核，保留仍有效的已完成实现，按影响和依赖重新验证
   - 内部实现变化 → 核对行为、状态和消费者影响，再确定实际回归范围，不机械重置所有模块
   - 删除导出 → 检查下游是否存在悬空依赖，如有则必须同步修改下游
5. 按更新后的项目架构修改代码 + 运行受影响模块的测试
6. 编码或测试中发现状态、异常、权限、数据、接口、反馈或验证责任缺口时，进入实现期功能族循环展开：暂停编码 → 更新架构切片 → 重新确认影响范围 → 继续实现

**安全修改模式**：

| 变更类型 | 影响范围 | 处理方式 |
|---------|---------|---------|
| 改函数内部实现 | 当前模块及实际行为受影响方 | 记录修改与验证责任→改代码→跑适用回归 |
| 新增导出接口 | 提供方及实际接入的消费者 | 更新权威契约与适用关系→加代码→验证调用边界 |
| 改接口参数（新增可选参数） | 当前模块与适用消费者 | 核对默认值、行为和错误语义，验证兼容性 |
| 改接口参数（改类型/删参数） | 当前+所有下游 | 先更新所有下游的调用代码，再改当前模块 |
| 改数据库表结构 | 当前+所有操作该表的模块 | 先写迁移脚本，再依次更新各模块 |
| 拆分模块 | 新增模块+原模块+下游 | 先创建新模块→迁移接口→更新下游引用→删除旧代码 |
| 合并模块 | 合并后的模块+下游 | 先创建合并模块→迁移所有接口→更新下游引用→删除旧模块 |

### `/追加架构` — 新增不存在的模块

**触发**：新增项目架构中不存在的模块/功能。

**流程**：
1. 从根逐层定位新增职责适合归属的模块，取得相关契约与源码；集中布局跟随总索引与登记
2. 功能簇标准展开（用户说的功能名 → 列出核心+天然绑定+适用商业标配+强相关衍生与关联功能全景 → 用户取舍与已有授权）
3. 功能树建模（把新增功能挂到既有功能域/功能组；没有合适父节点时新增功能域）
4. 专业能力索引匹配（如页面/UI、E2E、安全、性能、客户端、可执行交付、部署、文档等需要专业能力）
5. 判断复用现有模块或创建新模块；新模块确定父级、真实目录、本模块架构与路由，任何一层可拥有实现
6. 补模块详情（职责、非职责、内部结构、数据读写、错误边界、配置、安全、测试责任）
7. 确认后自动拆块 → 逐块深度设计 → 自动推进
8. 全部完成后汇报

**单块模式**：如果新增内容不超过一个块的规模，直接深度设计+编码+测试。

### `/校验架构` — 校验项目架构与代码一致性

**触发**：用户要求检查项目是否漂移，或在完成创建/分析/追加/修改后收尾验证。

**流程**：
1. 从有效入口读取项目骨架、相关模块的契约、清单和细节；递归布局检查路由、唯一编号、职责摘要和文件归属
2. 对照代码目录、入口、路由、接口、数据结构、测试文件
3. 检查代码中是否存在项目架构未定义的模块/文件/接口
4. 检查项目架构中定义但代码缺失、测试缺失或状态过期的节点
5. 输出一致性报告：通过项、偏差项、风险等级、建议修复顺序
6. 如用户要求修复，先更新架构切片，再按 `/修改架构` 或 `/追加架构` 执行

**输出必须包含**：
- 总体结论：一致 / 轻微漂移 / 严重漂移
- 偏差清单：架构有代码无、代码有架构无、契约不一致、测试缺失
- 影响范围：受影响模块、接口、页面、数据、测试
- 修复建议：先改架构切片、先改代码、或需要用户确认的分歧点

**偏差分类**：
- 架构漏登记：代码真实存在且合理，先补架构切片，再校验
- 代码越界：代码超出架构定义且无合理依据，回收代码或先登记后评估
- 架构设计错误：先修改架构切片，再按新架构修改代码
- 真实代码代表现状：走 `/分析架构` 同步现状，再输出治理建议

### 漂移修复模式

当发现项目架构与代码不一致时，不要直接“以代码为准”或“以架构为准”。先分类，再修复。

```
发现漂移
  ↓
列出差异：代码有架构无 / 架构有代码无 / 契约不一致 / 测试缺失 / 验证证据缺失
  ↓
判断来源：
  A. 合理实现但漏登记 → 先补架构切片，再校验
  B. 临时实现或越界实现 → 回收代码，或先登记为待确认再评估
  C. 架构设计过期 → 先更新架构切片，再按新架构改代码
  D. 需求不清导致分歧 → 写入未决问题，暂停破坏性修改
  ↓
补齐：功能树、模块树、模块详情、接口契约、实现清单、测试责任、验证证据
  ↓
运行受影响测试和 21 项校验
  ↓
写入变更记录：漂移类型、修复方式、影响范围、剩余风险
```

**漂移修复优先级**：
1. 先修契约漂移：接口签名、路由、数据结构不一致会影响下游。
2. 再修落位漂移：文件、模块树、实现清单缺登记会影响可追踪。
3. 再修测试漂移：功能已变但测试责任未更新。
4. 最后修文档性漂移：说明、状态、恢复点过期。

**禁止**：
- 不得因为“代码已经能跑”就跳过架构补登记。
- 不得把明显越界代码直接登记成正式设计，除非先评估其功能树、模块树和依赖影响。
- 不得只改架构切片不处理代码中已经存在的冲突实现。

## 状态流转

```
模块状态：计划中 → 编写中 → 待测试 → 测试中 → 已完成
              │         │           │
              └── 已废弃 ←── 修复中 ←─┘

文件状态：计划中 → 编写中 → 已完成 → 待审查
              │         │
              └── 已废弃 ←── 修复中
```

**转换规则**：
- 依赖契约明确后可推进本模块实现；未完成的依赖可用明确的替身验证局部行为，但集成状态保持未验证，不能宣称整体完成
- 本模块自有文件完成后可进入"待测试"；子模块与集成验收单独核对，父目录包含不自动等于子模块已完成
- 测试失败 → 相关模块和文件变为"修复中"

## 拆分原则

**应该拆**（满足任一）：有独立对外接口、被其他模块依赖、可独立编译测试、职责明显不同、可作为父模块下稳定子模块。
**不应该拆**：只有目录形式变化、内部辅助细节或拆分会制造紧密耦合且没有独立职责/验证收益。
**粒度**：按职责、契约、状态归属与理解/验证成本决定。文件数量、行数和深度只是调查线索，不作强制拆分或合并门槛；不限制语言和工程格式。

**三层粒度**：
- 功能粒度：拆到可验收、可落位、可测试。
- 模块粒度：拆到有父子归属、职责边界、接口/文件/数据/测试落位。
- 文件粒度：拆到文件职责单一，继续拆会变成函数级细节。

## 工作流程

### 执行前门禁

入口、授权、状态、任务类型与可见回执沿用 [LAYER](../../skills/xl-ai-language/LAYER.md)，进入本工作流不重复初始化或贴长模板。当前入口或事实明显过期时先 `/校验架构` 分类；已有模块加文件/导出属于修改，新模块属于追加。明确本次模块、契约、文件、数据、交互与测试的最低交付条件，补实际变化的权威事实后实施。

记录与失败恢复参考 [执行记录](execution-templates.md)，完成前核对其完成定义。内部判断不要求逐项对外打印；详细证据唯一维护，恢复位置引用它。

### 实现期功能族循环展开

设计好架构并开始编码后，架构不是冻结的。实现过程中如果发现当前功能节点的自然边界还没有展开完整，应进行局部循环，而不是把发现的能力直接写进代码。

```text
当前模块开始实现
  ↓
发现缺口：状态 / 异常 / 权限 / 数据 / 接口 / 交互反馈 / 测试责任
  ↓
停止当前代码修改
  ↓
回到拥有当前功能事实的根/模块架构或既有切片展开当前功能族或子功能节点
  ↓
分类：必须补 / 建议补 / 待确认 / 明确排除
  ↓
更新功能树、模块详情、接口契约、实现清单、测试责任
  ↓
继续实现并验证
  ↓
叶子节点闭合后退出循环
```

循环边界：
- 只展开当前模块、当前功能节点和直接依赖契约，不借机全局重构。
- 必须补内容可以进入本轮；建议补和待确认内容不得悄悄实现。
- 用户明确不要的内容优先排除，并写入恢复点或非目标。
- 循环退出后必须有验证证据或明确阻塞原因。

### 受管项目默认路由

当项目中存在根入口 `architecture.json` 或有效集中入口 `architecture/index.json` 时，用户即使没有输入命令，也按以下规则自动路由。用户只说“使用 Xl-Ai-Language”“按这个技能”“按架构来”“按照 architecture.json”时，也必须先自动判断命令类型，不得等待用户补命令或直接改代码。

| 用户说法 | 默认命令 | 说明 |
|------|------|------|
| “使用 Xl-Ai-Language/按这个技能/按架构来” | 自动判定 | 根据后续任务内容选择分析、创建、修改、追加或校验 |
| “改一下页面/删掉标题/调整按钮/优化 UI” | `/修改架构` | UI 属于页面拓扑、完整细节和验证证据的一部分 |
| “修一个 bug/报错/异常” | `/修改架构` | 先补 Bug 场景、异常路径和测试责任，再修代码 |
| “新增独立功能/新增模块” | `/追加架构` | 新职责先充分设计再落位；已有模块职责内新增页面、文件、导出或入口用 `/修改架构`，不为命令类型强拆模块 |
| “改字段/表结构/接口参数” | `/修改架构` | 先更新数据拓扑或接口契约，再改迁移/代码 |
| “重构/优化性能/调整目录” | `/修改架构` | 先更新影响范围、模块状态和变更记录 |
| “检查是否一致/为什么不对” | `/校验架构` | 先分类架构漏登记、代码越界或架构设计错误 |

禁止把“很小的修改”当作绕过项目架构的理由。受管项目的小修改也会导致长期漂移。

### 无命令自动判定规则

用户没有写 `/分析架构`、`/创建架构`、`/修改架构`、`/追加架构`、`/校验架构` 时，按以下顺序判定：

1. 要求检查、评估一致性、找漂移、解释为什么不对 → `/校验架构`
2. 已有代码但没有可信项目架构入口，要求纳入管理 → `/分析架构`
3. 没有代码或明确从零开始 → `/创建架构`
4. 要增加独立功能或模块职责 → `/追加架构`
5. 要改已有职责内的功能，含新增页面、文件、导出或接口，以及修 Bug、删 UI、改字段、调样式、优化性能、重构已有模块 → `/修改架构`

第一段汇报必须写明“自动判定命令：...”。若无法判定，先问一个澄清问题，不得先改代码。

### 从项目架构到代码

```
根总架构与相关模块职责、契约就绪
    ↓
按优先级顺序，每个模块：
  1. 从根读取全局目标约束与当前工作状态
  2. 沿相关模块路由逐层定位，确认目标自己的实现和必要子模块
  3. 读本模块详情确认职责、非职责、内部结构、数据责任、生命周期和错误边界
  4. 读第2层获取当前模块的接口契约（导出什么+依赖谁）
  5. 读第3层获取文件清单+数据表DD→创建目录和文件骨架
  6. 读第4层获取当前模块的完整细节→按接口签名填充实现→按测试用例生成测试
  7. 运行适用测试与质量检查 → 记录已验证范围及未验证项 → 满足本模块完成条件后进入下一模块；集成独立验收
```

**四层读取逐模块递进**：写 m6 时读本模块相关细节、必要依赖契约与实际源码；行为影响消费者时扩展相应范围。不读无关细节，不把按需读取当作省略必要设计和验证的理由。

### 完整开发流程

```
/创建架构 或 /分析架构 → 项目架构就绪
    ↓
逐块设计 + 编码 + 测试 → 自动推进直到全部"已完成"
    ↓
集成验证 → 最终产物
```

### 中断恢复

动手前自检：说不出「当前任务/当前阶段/下一步」即视同已被压缩，先按 [上下文恢复](context-recovery.md) 读恢复点再动作。

读取根或已登记任务记录的 `上下文恢复点`、已有阶段状态与相关模块交接信息，核对哪些已完成、哪些进行中、下一步和未验证事项；恢复点与实际版本需要交叉核对。集中布局标准任务位置为 `architecture/tasks/state.json`。

恢复顺序：
1. 读取 `上下文恢复点`：当前任务、当前阶段、继续位置、下一步、未验证项、用户明确约束。
2. 读取第1层项目骨架和当前模块的第2-4层。
3. 检查 `已触碰文件` 和实际文件差异，确认是否有未记录代码漂移。
4. 从 `下一步` 的第一项继续，不要从头重新设计。
5. 完成后更新 `上下文恢复点`、`验证证据` 和 `变更记录`。

如果项目启用了 `架构切片`，恢复时先读根 `architecture.json`；若它指向 `architecture/index.json`，必须转读项目架构总索引，再只读取 `进行中模块` 或 `下一步` 指向的切片。切片细节见 [JSON 切片协议](json-sharding.md)。

### 调试与排错

**项目架构也是排错地图。当出现 Bug 时，利用架构切片中的以下信息快速定位：**

**定位流程**：
```
Bug 报告 → 确定出问题的模块编号
    │
    ├── 查架构切片的依赖字段 → 是上游传错数据，还是本模块逻辑错误？
    │   如果上游接口返回的数据不对 → 追溯到上游模块
    │
    ├── 查架构切片的接口.导出 → 实际调用参数是否符合接口签名？
    │   参数类型不匹配 → 调用方的问题
    │   参数正确但结果错误 → 本模块实现问题
    │
    ├── 查架构切片的接口.可能异常 → 这个异常是否被正确处理？
    │   未列出的异常 → 架构定义不完整，需更新
    │   已列出但未捕获 → 代码实现遗漏
    │
    └── 查架构切片的测试用例 → 这个 Bug 场景是否有覆盖？
        没有 → 先补测试用例到架构切片，再修代码
        有但测试未发现 → 测试实现有误，修正测试
```

**常见排错模式**：

| 症状 | 架构诊断 | 修复方式 |
|------|---------|---------|
| 模块A调用模块B报错 | 检查B的接口签名和可能异常 | 如A的参数不符合签名→修A；如B少列了异常→更新B的架构切片 |
| 数据表字段缺失 | 检查数据架构中的表定义 | 表定义不完整→`/修改架构`补字段+写迁移 |
| 组件状态异常 | 检查组件的状态展示五态定义 | 某态未定义→补定义；实现不符合定义→修代码 |
| 循环依赖报错 | 检查依赖图 | `/修改架构`重构去除循环 |
| 测试通过但线上异常 | 检查测试用例是否覆盖该场景 | 补测试用例到架构切片→补测试代码→复现→修复 |

**修复后必须做的事**：
1. 更新架构变更记录（原因写明 Bug 根因）
2. 补充测试用例到架构切片（覆盖本次 Bug 场景）
3. 检查是否有同类问题存在于其他模块（同类接口、同类组件）

### 项目优化

**优化项目先确定设计与影响，再同步所属架构记录和相关实现。** 可以精确修改已有代码，不因优化而重新生成无关文件或要求先全量迁移架构布局。

**优化发现**：在任务需要时检查根与相关模块记录中的以下信号，发现优化候选：

```
信号1: 模块出现多项独立职责或验证成本过高 → 调查是否需要子模块
信号2: 细小模块没有独立契约收益且频繁共同修改 → 调查是否过度拆分
信号3: 目录或依赖层级增加但不帮助职责定位 → 调查是否存在无效层次
信号4: 多模块依赖同一能力 → 区分合理公共能力与职责过于集中
信号5: 测试用例仅覆盖 happy path → 补充边界和异常测试
信号6: 变更记录中同一模块频繁修改 → 接口设计可能不稳定
信号7: 多个模块有相同的导出签名 → 提取公共接口/基类
信号8: 组件树的属性很多但默认值为空 → 组件可能过度设计
```

**优化决策矩阵**：

| 优化目标 | 识别方式 | 操作 |
|---------|---------|------|
| 性能优化（接口不变） | 分析/监控发现瓶颈 | 更新目标模块变更记录 → 改实现 → 跑测试 |
| 重构拆分 | 职责混杂或理解/验证成本过高 | `/修改架构`设计合理子模块 → 维护路由、接口与归属 → 精确迁移受影响实现 |
| 重构合并 | 小模块且高度耦合 | `/修改架构`合并 → 更新接口列表 → 合并代码 |
| 消除循环依赖 | 依赖图分析发现环 | `/修改架构`重构依赖关系 → 可能需要提取公共接口 |
| 补充测试覆盖 | 测试用例缺少边界/异常 | 更新架构切片测试用例 → 补测试代码 |
| 升级框架/库 | `项目` 中的版本号 | `/修改架构`更新 `项目` + 受影响模块接口 → 逐模块适配 |
| 提取公共代码 | 多模块重复的导出签名 | `/追加架构`新增公共模块 → `/修改架构`让各模块依赖公共模块 |

**优化原则**：
- 先确认设计与影响并更新所属架构，再改相关实现；路由与共同约束变化时同步必要上层
- 一次优化只做一件事——不要同时拆分+合并+升级
- 每次优化后跑全部受影响模块的测试——不只是当前模块
- 优化完成后在变更记录中注明"为什么优化"（性能数据？可维护性？）

### 架构切片

新项目默认递归模块，协议见 [递归模块架构](recursive-modules.md)。既有集中切片按总索引登记局部事实，协议见 [JSON 切片协议](json-sharding.md)。两种布局都从有效根入口定位，事实唯一维护，工具合成只读视图。

启用前提：
- 集中布局的根 `architecture.json` 作为指针，不能据此限制递归布局的真实根总架构。
- 总入口与其登记事实共同回答项目身份、全局约束、模块关系、事实位置与恢复入口，不要求原始总索引重复下层细节。
- 每个切片只承载一个功能域、模块、页面、数据对象或当前任务。

执行规则：
1. 仅采用集中布局时，先创建有效的 `architecture/index.json` 与根指针，再创建或登记切片；递归模块按其协议创建真实模块目录和路由。
2. 全局关系由登记的关系记录持有或从局部契约合成，不在总索引重复维护同一依赖图。
3. 修改所属事实后更新本次变更；登记、路由或摘要变化时同步相关入口。
4. 总索引与切片冲突时，先走 `/校验架构` 分类，不得直接覆盖。

模块创建、查询、路由、影响和精确更新使用 `module_architecture.py`；确定性结构检查之外，继续执行既有占位符、一致性、漂移、质量和真实行为验证。
