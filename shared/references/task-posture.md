# 任务姿态与动态姿势语境

> 原 `dynamic-posture-context.md`（正式姿势语境）已合并入本文件第二节；旧记录中指向
> dynamic-posture-context.md 的引用以本文件为准。

任务姿态用于把智能体从普通聊天状态校准到工程执行状态。它不是情绪管理，也不是外部自动调度系统；它只回答一个问题：本次任务开始时，模型应该以哪些执行角色、任务场景、专业领域和约束来工作。

本文件分两层：**轻量姿态建议**（任务开始时的快速校准）与**正式姿势语境**（中大型/跨模块/高风险/跨会话任务的完整状态结构）。小任务只用第一层的一句话判定，不得强制输出完整语境。

## 一、轻量姿态建议

### 基本原则

- 姿态判定必须发生在写代码之前。
- 姿态只做执行重点、参考文件和校验项建议，不接管需求判断。
- 姿态结果必须服从用户明确不要、安全风险、架构先行和本次需求锁定。
- 姿态可以叠加，但必须按三轴理解：执行角色负责主流程，任务场景负责风险/阶段/恢复类约束，专业领域负责 UI、数据、接口等专项细节。
- 工具输出只是建议；若脚本判断与真实上下文冲突，以人工架构判断为准，并在汇报中说明修正理由。

检测器使用关键词生成建议，不解析完整自然语言语义，否定句中的 UI、数据库等词也可能命中。明确排除的能力仍保持不适用，不得仅凭命中项追加实现。能力层中的 `dynamic`、`linear`、`reactive` 描述流程选择；检测器的三轴描述参与职责与检查重点，两者分别判断，不要求工具返回同名的流程字段。

### 三轴分类

| 轴 | 含义 | 常见项 | 用法 |
|---|---|---|---|
| 执行角色 | 本次任务主流程中需要哪类工程职责 | 架构师、工程师、审计员 | 默认至少覆盖架构判断、实现执行、验证审计 |
| 任务场景 | 本次任务处于什么风险、阶段或恢复状态 | 修复模式、恢复、风险模式、交付模式 | 用来追加禁止事项、确认项和验证重点 |
| 专业领域 | 本次任务涉及哪个专业细节域 | UI设计、数据、接口、安全、测试、部署 | 用来按需读取 references 和补专项验收 |

姿态分类使用 `执行角色`、`任务场景`、`专业领域` 三轴。将相关建议落实到本次阶段、范围与验证重点；需要持久接力信息时才采用下方「正式姿势语境」，不为小任务生成完整对象。

### 姿态列表

| 姿态 | 所属轴 | 触发信号 | 必须动作 | 禁止事项 |
|---|---|---|---|---|
| 架构师 | 执行角色 | 新功能、模糊需求、模块新增、大改动、用户只说目标 | 功能族展开、功能树落位、模块影响分析、更新架构切片 | 直接写代码、把功能做成薄 demo |
| 工程师 | 执行角色 | 架构切片已更新、实现清单已确认、进入代码修改 | 按实现清单改代码、补测试、保持文件职责一致 | 新增未登记文件、绕过接口/数据契约 |
| 审计员 | 执行角色 | 代码修改完成、提交前、用户要求检查、长期未维护 | 运行校验、记录验证证据、写剩余风险、检查漂移 | 无验证直接结束、只报喜不报风险 |
| UI设计 | 专业领域 | 页面、组件、菜单、表单、图标、交互、响应式、截图验收 | 展开状态、反馈、异常、权限、响应式、可访问性、图标语义 | 只画静态界面、只加按钮不补交互闭环 |
| 恢复 | 任务场景 | 上下文压缩、中断、换会话、用户说继续 | 读取上下文恢复点、变更记录、未决问题和最近验证 | 凭记忆续写、忽略已触碰文件 |
| 风险模式 | 任务场景 | 删除、迁移、权限、安全、支付、金融、外部服务、不可逆操作 | 标注风险等级、列出待确认项、必要时询问用户 | 默认执行高风险动作、把待确认当已确认 |
| 修复模式 | 任务场景 | 测试失败、构建失败、运行报错、用户要求修 Bug | 复现/定位、最小修复、补验证、回写影响范围 | 大范围重构、顺手改无关功能 |
| 交付模式 | 任务场景 | EXE、安装包、Docker、SDK、插件、CLI、桌面端、发布部署 | 检查入口、配置、资源、版本、安装/卸载、发布验证 | 只改业务代码不验证交付形态 |

### 姿态输出模板

任务开始时把判断合并到 LAYER 的一次简短回执；下方为可选结构示例，不要求另贴完整工具输出。

```json
{
  "任务类型": ["UI", "数据导出"],
  "受管项目": true,
  "风险等级": "中",
  "置信度": "中",
  "命中依据": ["任务类型:UI:页面", "任务类型:数据:导出", "姿态:UI设计:按钮"],
  "执行角色": ["架构师", "工程师", "审计员"],
  "任务场景": [],
  "专业领域": ["UI设计"],
  "必须加载": ["architecture.json", "相关分支的模块架构与契约"],
  "按需加载": [
    "references/function-clusters.md",
    "references/interaction-completeness.md"
  ],
  "必须校验": ["导出权限", "空数据", "大数据量", "失败反馈", "测试证据"],
  "禁止事项": ["直接写代码", "跳过 JSON", "只加按钮不补导出闭环"],
  "裁决边界": "本结果只做任务前提醒，不替代用户明确需求、安全风险裁决、功能族展开、当前项目有效根入口与登记模块/切片的事实和模型工程判断。"
}
```

字段解释：

- `置信度`：只表示关键词命中覆盖度，不代表工程判断正确性。
- `命中依据`：说明脚本为什么给出这些建议，便于模型人工修正。
- `执行角色`：本次任务需要承担的主流程工程职责。
- `任务场景`：本次任务附加的风险、恢复、修复或交付场景。
- `专业领域`：本次任务涉及的专项能力域，如 UI设计。
- `必须加载`：任务开始必须读取或确认的文件。受管项目从根 `architecture.json` 逐层读取相关分支；已有集中布局按实际索引与切片读取；未纳管时从 `SKILL.md` 开始，辅助 `architecture/` 目录本身不证明集中索引存在。
- `按需加载`：只有当本次任务确实涉及对应细节时再读取，避免规则挤占注意力。
- `裁决边界`：提醒脚本不是裁判，最终仍由任务架构规则和真实上下文裁决。

### 脚本建议器

可运行 `shared/scripts/detect_task_posture.py --request "用户需求"` 获取初始建议。脚本只根据关键词、项目是否受管（`architecture.json` 或 `architecture/`）和轻量规则输出建议，不读取业务代码，不修改文件，不替代模型的工程判断。若 `置信度=低` 或 `命中依据` 与真实上下文不符，必须人工修正姿态、加载文件和校验项。

### 专业能力的动态加载

姿态给出当前阶段、作用域和验证重点；专业能力选择还须依据本次已确认需求、功能节点、模块、风险、明确排除和实际可用性。检测器输出只是候选，不能把否定句、角色名或“验证阶段”转换为新增专项授权。主会话根据现有需求与项目事实完成判断，不要求用户反复确认。

按 `capability-index.md` 使用宿主给出的技能名称/描述/路径元数据构造最小catalog，或使用内置专业资料。运行 `plan_capabilities.py` 后用宿主原生读取工具加载所选 `read_files`；没有系统提示注入API时，只表述“按需载入上下文”。计划成功不能证明已读取文件，更不能证明专项检查通过。

| 阶段/变化 | 加载与核验动作 |
|---|---|
| 需求或架构设计 | 先确认本次能力需求与范围；只加载帮助当前决策的资料 |
| 实现或验证，且需要代码正确性审查 | 载入代码语义审查资料；自动执行与审查结论分别记录 |
| 跨模块协作、换执行者或恢复 | 载入交接完整性资料，核对原约束、ID、输入版本和部分失败 |
| 转换/迁移/导出/回写进入验证或交付 | 载入产物完整性资料，独立核对来源、产物与架构回写 |
| 阶段、需求、范围、风险或输入发生变化 | 重新规划，说明新增/保留/退出能力；原失败与未解决约束继续保留 |

完全跳过档不规划、不建状态。最小闭环只加载当前必需内容，可用一句话说明选定能力、实际加载、范围与未验证项；需要机器复核的调用再保存最小记录。长任务与跨会话将计划/实际使用位置和未解决约束写入既有恢复点，不另建总控状态系统。

规划语境可用下列精简形式，字段值由当前任务确定，不能照抄样例当作授权：

```json
{
  "stage": "验证",
  "tier": "full",
  "module_ids": ["m_store"],
  "professional_domains": ["代码质量"],
  "confirmed_capabilities": ["代码语义审查"],
  "required_capabilities": [],
  "excluded_capabilities": [],
  "risks": ["正确性"],
  "read_scope": ["src/**", "tests/**", "architecture/**"],
  "write_scope": ["architecture/**"]
}
```

所需资料不可用或预算不足时保留缺口；可调整相称预算或分阶段读取必要内容，不静默截断必需约束。是否停止由当前验收、风险、授权和未解决问题决定，专项退出不等于整体完成。

## 二、正式姿势语境

动态姿势语境用于描述智能体当前处在什么工程状态。它不是角色身份，也不是多智能体调度结果，而是影响读取范围、功能族展开深度、模块行为、硬门禁和验证责任的状态系统。

### 标准结构

下方为中大型、跨模块、高风险、交付或恢复任务可用的语境示例。只保存本次读取、执行、验收与接力需要的信息；已有架构/任务记录可引用，不要求每轮展开完整JSON。小任务使用一句话或精简记录。

```json
{
  "姿势语境": {
    "版本": "1.0",
    "语境编号": "ctx_001",
    "作用域": "全局 | 模块 | 接口 | 数据 | UI | 交付 | 恢复",
    "当前阶段": "需求锁定 | 架构设计 | 架构更新 | 实现 | 验证 | 收尾 | 恢复 | 阻塞",
    "任务类型": ["新增功能"],
    "执行模式": ["规划", "模块设计", "实现", "审查", "修复", "风险控制"],
    "专业语境": ["UI", "接口", "数据", "安全", "测试", "性能", "部署"],
    "风险等级": "低 | 中 | 高 | 阻塞",
    "触发事件": [],
    "生效原因": [],
    "适用模块": [],
    "模块关系": {
      "主改模块": [],
      "受影响模块": [],
      "只读依赖模块": [],
      "下游消费者": []
    },
    "必须读取": [],
    "必须校验": [],
    "硬约束追加": [],
    "禁止事项": [],
    "功能族展开策略": {
      "展开深度": "浅 | 中 | 深",
      "默认纳入": [],
      "待确认扩展": [],
      "明确排除": []
    },
    "退出条件": [],
    "裁决优先级": [],
    "更新时间": "ISO-8601"
  }
}
```

### 分级使用

| 任务规模 | 输出形式 | 适用场景 |
|---|---|---|
| 小任务 | 一句话语境 | 改文案、改样式、小 Bug、单文件内部调整 |
| 中任务 | 精简 JSON | 单模块功能修改、接口小改、普通 UI/数据变更 |
| 大任务 | 必要的持久语境，引用已有事实 | 新功能、跨模块变更、高风险操作、交付发布、恢复续跑 |

#### 小任务语境

```text
阶段=实现；风险=低；作用域=m_ui；禁止=不碰无关模块；校验=页面显示/相关测试。
```

#### 中任务语境

```json
{
  "当前阶段": "实现",
  "风险等级": "中",
  "适用模块": ["m_export"],
  "受影响模块": ["m_auth"],
  "必须校验": ["权限", "失败反馈"],
  "禁止事项": ["跳过 JSON", "顺手改无关模块"],
  "退出条件": ["验证证据已记录"]
}
```

#### 大任务语境

跨会话、长任务或高风险任务保存继续执行所需的语境；写入实际入口登记的根恢复点或任务记录。既有集中布局可用 `architecture/tasks/state.json`；递归布局由根引用模块交接信息。按 [上下文恢复](context-recovery.md) 保持一份权威记录，不因语境变化另建相同状态。

### 动态触发

| 触发事件 | 语境变化 |
|---|---|
| 用户需求模糊 | 进入需求锁定和功能族展开语境 |
| 发现根架构 `architecture.json` 或 `architecture/` 辅助目录 | 进入受管项目语境，按真实入口逐层读取相关模块或集中切片；只有辅助文件时先确认并建立架构入口，已登记入口失效先修复 |
| 新增模块或功能 | 进入架构设计和模块设计语境 |
| 修改接口签名 | 进入接口契约和下游影响语境 |
| 涉及删除、迁移、权限、生产数据 | 进入高风险语境 |
| 开始修改代码 | 进入实现语境 |
| 测试失败 | 进入修复语境，冻结无关扩展 |
| 准备构建、发布、打包 | 进入交付语境 |
| 上下文中断或用户说继续 | 进入恢复语境 |

### 硬规则

- 每次语境变化必须有触发事件。
- 语境可以追加约束，不能移除核心硬约束。
- 高风险语境优先级高于普通实现语境。
- 修复语境禁止顺手重构和无关扩展。
- 恢复语境必须先读取恢复点和最近变更记录。
- 恢复时核对已选择/实际加载/已使用的专业能力与当前文件；旧计划、旧审查和旧收据不能替代当前证据。
- 语境退出必须满足明确退出条件。
- 小任务不强制完整 JSON；如果完整语境开始挤压实现和验证，应降级为一句话或精简 JSON。

## task_state.json 边界

默认复用已登记的阶段状态与恢复点，不创建 `task_state.json`。只有独立任务状态确有职责、且现有记录不能承载时才建立；先在权威架构登记位置与用途，引用已有约束、证据和进度，不维护第二份同一状态。

推荐结构：

```json
{
  "当前姿态": "架构师",
  "任务类型": ["UI", "功能新增"],
  "需求锁定": "给选股结果页增加导出能力",
  "已完成": ["读取根架构及相关模块契约", "功能族展开"],
  "下一步": "沿实际入口更新拥有本次事实的模块架构",
  "禁止事项": ["直接写代码", "跳过验证"],
  "风险": ["导出权限", "大数据量"]
}
```
