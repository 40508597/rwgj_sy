# 模块智能体协议

模块智能体是按模块边界组织的虚拟或真实执行单元，以项目总目标、模块职责、接口契约、功能树与模块详情为边界。根和模块架构保存知识与工作状态，具体执行者可以更换；不把模块永久绑定某个智能体，也不强制每个任务并发执行。职业型专业子技能可以辅助工作，不替代模块责任。

## 模块智能体定义

需要实际登记责任、协调共同变更和交接时，使用 [项目工具链](./project-toolchain.md) 中 lease、change coordinate、handoff。责任属于模块，执行者可替换；租约不等于系统写权限。参与者就绪绑定当前输入、暂存操作与恢复分支，旧证据不能直接接受。

```json
{
  "智能体编号": "agent_auth",
  "负责模块": "m_auth",
  "架构路径": "modules/auth/architecture.json",
  "模块目标": "",
  "可修改范围": [],
  "只读依赖": [],
  "可导出接口": [],
  "禁止事项": [],
  "完成条件": []
}
```

## 执行边界

模块智能体可以：

- 从根 `architecture.json` 的目标、全局约束与路由逐层进入所属模块，读取相关功能、模块细节、上游契约、下游消费者、源码与测试；既有集中布局跟随指针及切片登记。如本次已有动态姿势语境，读取项目恢复点中的相关任务语境。
- 使用功能族展开本模块应承担的能力。
- 提出模块内变更、接口变更、跨模块提案和验证责任。
- 修改本次分工授权且归属本模块的文件。父模块拥有自己的实现，但不因包含子模块目录就自动获得其并发写入责任。

模块智能体不得：

- 在未协调本次责任范围时直接修改其他执行者负责的文件；跨模块任务可以明确分配多个模块，不把权限永久限定为单模块。
- 绕过接口契约调用其他模块内部结构。
- 私自改变公共接口。
- 将待确认扩展直接实现。
- 把功能族候选当作已确认需求。

## 功能族使用

每个模块智能体都可以使用功能族，但必须分类：

```json
{
  "功能族展开": {
    "核心功能": [],
    "天然绑定功能": [],
    "商业标配功能": [],
    "待确认扩展": [],
    "跨模块提案": [],
    "明确排除": []
  }
}
```

尚未裁决的跨模块提案进入提案与接口契约记录，不直接当作已确认需求实现。已有授权和已确认方案内的跨模块修改可以继续推进，先明确事实归属、协作分工和影响；公共文件由一个执行者负责写入或通过版本校验合并，避免覆盖。

## 模块提案输出

模块智能体输出必须符合 [提案契约](agent-output-contract.md)。最低要求包含：输出类型、关联语境、负责范围、结论、功能族展开、变更提案、接口影响、风险、验证责任、证据和下一步。

## 专业能力与交接

模块执行者按 `capability-index.md` 从已确认任务、模块、风险与当前姿态选择专业技能；只读取选中文件，不接管其他模块或注册中央调度器。阶段/输入变化重新核对计划，实际使用与产出回写留在调用方项目。

跨执行者、恢复或部分结果合并时按需读 `handoff-integrity.md`：保留原约束、ID、接口影响、失败/部分完成、证据版本和退出条件。各模块完成不代表集成已验收，冲突结果需带证据裁决。质量专项遵循 `universal-quality.md`，缺必需事实或本次执行证据仍是未验证。

模块分工时交接当前目标、路由路径、基准版本、已触碰文件、有效决策、未完成事项、未验证项与下一步。执行者退出后这些信息留在调用方项目；后续执行者从根核对最新事实与实际差异，不仅凭上一位的完成描述继续。目录与源码归属规则见 [递归模块架构](recursive-modules.md)，状态恢复见 [上下文恢复](context-recovery.md)。
