# 上下文压缩恢复协议

## 目标

用 `architecture.json` 对抗对话压缩、会话中断和多轮遗忘。任何只存在于对话里的关键事实，都可能在压缩后丢失；因此必须把继续开发所需的最小事实写入 `上下文恢复点`。

## 何时更新

在以下时机必须更新：

1. 每轮完成前。
2. 修改 architecture.json 后。
3. 跑完测试或验证后。
4. 遇到阻塞、未验证项、用户明确约束或用户明确不要时。
5. 即将停止、等待用户、上下文变长或任务跨会话时。

## 字段要求

```json
{
  "上下文恢复点": {
    "当前任务": "本轮正在完成的目标",
    "当前阶段": "分析/设计/实现/测试/修复/校验/收尾",
    "继续位置": "下一轮应该从哪里继续",
    "最近完成": ["刚完成的事实，不写泛泛总结"],
    "下一步": ["按顺序列出可执行动作"],
    "进行中模块": ["m1"],
    "已触碰文件": ["architecture.json"],
    "已运行命令": ["python -m pytest"],
    "用户明确约束": ["用户要求 JSON 字段名中文"],
    "用户明确不要": ["用户不要多智能体"],
    "待确认问题": ["需要用户决策的问题"],
    "未验证项": ["尚未验证的行为"],
    "剩余风险": ["已知残余风险"],
    "压缩摘要": "给下一个智能体的短摘要",
    "更新时间": "ISO 8601 时间"
  }
}
```

## 恢复流程

压缩、中断或新会话恢复时：

1. 先读 `architecture.json.上下文恢复点`。
2. 再读第1层项目骨架。
3. 只读 `进行中模块` 相关的第2-4层。
4. 检查 `已触碰文件` 与实际文件是否一致。
5. 从 `下一步[0]` 继续，不从头重新设计。
6. 如果恢复点与代码冲突，先走 `/校验架构` 分类偏差。

## 写入原则

- 写事实，不写空话。
- 写下一步，不只写已完成。
- 写用户明确不要，防止功能簇展开把它重新带回来。
- 写未验证项，防止“测试通过”掩盖未覆盖路径。
- 写剩余风险，防止下一轮把风险当成已解决。

## 禁止

- 只在最终回复里说明继续位置，不写入 JSON。
- 用长篇对话摘要替代结构化恢复点。
- 把所有历史都塞进恢复点；恢复点只保存下一轮继续所需的最小事实。
- 压缩后凭记忆继续，不读取恢复点。
