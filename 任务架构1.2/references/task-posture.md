# 动态任务姿态

任务姿态用于把智能体从普通聊天状态校准到工程执行状态。它不是情绪管理，不是假装有多个智能体，也不是自动调度系统；它只回答一个问题：本次任务开始时，模型应该以哪些执行角色、任务场景、专业领域和约束来工作。

## 基本原则

- 姿态判定必须发生在写代码之前。
- 姿态只做执行重点、参考文件和校验项建议，不接管需求判断。
- 姿态结果必须服从用户明确不要、安全风险、JSON 先行和本次需求锁定。
- 姿态可以叠加，但必须按三轴理解：执行角色负责主流程，任务场景负责风险/阶段/恢复类约束，专业领域负责 UI、数据、接口等专项细节。
- 工具输出只是建议；若脚本判断与真实上下文冲突，以人工架构判断为准，并在汇报中说明修正理由。

## 三轴分类

| 轴 | 含义 | 常见项 | 用法 |
|---|---|---|---|
| 执行角色 | 本次任务主流程中需要哪类工程职责 | 架构师、工程师、审计员 | 默认至少覆盖架构判断、实现执行、验证审计 |
| 任务场景 | 本次任务处于什么风险、阶段或恢复状态 | 修复模式、恢复、风险模式、交付模式 | 用来追加禁止事项、确认项和验证重点 |
| 专业领域 | 本次任务涉及哪个专业细节域 | UI设计、数据、接口、安全、测试、部署 | 用来按需读取 references 和补专项验收 |

输出只保留 `执行角色`、`任务场景`、`专业领域` 三轴字段，不再保留旧的 `必须姿态`、`建议姿态` 兼容字段，避免把姿态误解成多智能体角色分配。

## 姿态列表

| 姿态 | 所属轴 | 触发信号 | 必须动作 | 禁止事项 |
|---|---|---|---|---|
| 架构师 | 执行角色 | 新功能、模糊需求、模块新增、大改动、用户只说目标 | 功能族展开、功能树落位、模块影响分析、更新 JSON | 直接写代码、把功能做成薄 demo |
| 工程师 | 执行角色 | JSON 已更新、实现清单已确认、进入代码修改 | 按实现清单改代码、补测试、保持文件职责一致 | 新增未登记文件、绕过接口/数据契约 |
| 审计员 | 执行角色 | 代码修改完成、提交前、用户要求检查、长期未维护 | 运行校验、记录验证证据、写剩余风险、检查漂移 | 无验证直接结束、只报喜不报风险 |
| UI设计 | 专业领域 | 页面、组件、菜单、表单、图标、交互、响应式、截图验收 | 展开状态、反馈、异常、权限、响应式、可访问性、图标语义 | 只画静态界面、只加按钮不补交互闭环 |
| 恢复 | 任务场景 | 上下文压缩、中断、换会话、用户说继续 | 读取上下文恢复点、变更记录、未决问题和最近验证 | 凭记忆续写、忽略已触碰文件 |
| 风险模式 | 任务场景 | 删除、迁移、权限、安全、支付、金融、外部服务、不可逆操作 | 标注风险等级、列出待确认项、必要时询问用户 | 默认执行高风险动作、把待确认当已确认 |
| 修复模式 | 任务场景 | 测试失败、构建失败、运行报错、用户要求修 Bug | 复现/定位、最小修复、补验证、回写影响范围 | 大范围重构、顺手改无关功能 |
| 交付模式 | 任务场景 | EXE、安装包、Docker、SDK、插件、CLI、桌面端、发布部署 | 检查入口、配置、资源、版本、安装/卸载、发布验证 | 只改业务代码不验证交付形态 |

## 姿态输出模板

任务开始时，用简短结构输出判断；不需要写长报告。

```json
{
  "任务类型": ["UI", "数据导出"],
  "受管项目": true,
  "风险等级": "中",
  "置信度": "中",
  "命中依据": ["任务类型:UI:页面", "任务类型:数据:导出", "姿态:UI设计:按钮"],
  "执行角色": ["架构师", "工程师", "审计员"],
  "任务场景": [],
  "专业领域": ["UI设计"],
  "必须加载": ["architecture.json"],
  "按需加载": [
    "references/function-clusters.md",
    "references/interaction-completeness.md"
  ],
  "必须校验": ["导出权限", "空数据", "大数据量", "失败反馈", "测试证据"],
  "禁止事项": ["直接写代码", "跳过 JSON", "只加按钮不补导出闭环"],
  "裁决边界": "本结果只做任务前提醒，不替代用户明确需求、安全风险裁决、功能族展开、architecture.json 真相源和模型工程判断。"
}
```

字段解释：

- `置信度`：只表示关键词命中覆盖度，不代表工程判断正确性。
- `命中依据`：说明脚本为什么给出这些建议，便于模型人工修正。
- `执行角色`：本次任务需要承担的主流程工程职责。
- `任务场景`：本次任务附加的风险、恢复、修复或交付场景。
- `专业领域`：本次任务涉及的专项能力域，如 UI设计。
- `必须加载`：任务开始必须读取或确认的文件，通常是 `architecture.json` 或 `SKILL.md`。
- `按需加载`：只有当本次任务确实涉及对应细节时再读取，避免规则挤占注意力。
- `裁决边界`：提醒脚本不是裁判，最终仍由任务架构规则和真实上下文裁决。

## 分级使用

- 小修小补：只做一句姿态判定，最小 JSON 更新和必要校验。
- 中型功能：输出姿态 JSON，读取相关 references，补功能树和实现清单。
- 大型改动或跨会话：输出姿态 JSON，并在 `上下文恢复点` 中记录当前姿态、已完成、下一步、禁止事项和风险。

## task_state.json 边界

默认不创建 `task_state.json`。只有出现长任务、跨会话、多模块重构、用户明确要求状态文件，或上下文压缩风险较高时，才可以创建任务状态文件。创建前必须先登记到 `architecture.json` 的实现清单或上下文恢复点。

推荐结构：

```json
{
  "当前姿态": "架构师",
  "任务类型": ["UI", "功能新增"],
  "需求锁定": "给选股结果页增加导出能力",
  "已完成": ["读取 architecture.json", "功能族展开"],
  "下一步": "更新 architecture.json",
  "禁止事项": ["直接写代码", "跳过验证"],
  "风险": ["导出权限", "大数据量"]
}
```

## 脚本建议器

可运行 `scripts/detect_task_posture.py --request "用户需求"` 获取初始建议。脚本只根据关键词、项目是否存在 `architecture.json` 和轻量规则输出建议，不读取业务代码，不修改文件，不替代模型的工程判断。若 `置信度=低` 或 `命中依据` 与真实上下文不符，必须人工修正姿态、加载文件和校验项。
